<objective>
Fix a confirmed production bug: transactional OTP SMS sent through Hablame's API are accepted (statusId 1) but never reach the recipient's device, because `HablameSmsService::sendRaw()` nests `priority` inside each `messages[]` entry instead of putting it (and `from`) at the ROOT of the JSON body, as Hablame's support and official docs require. `send()` (bulk SMS) has the same missing-`from`-at-root problem. A separate, already-confirmed routing bug in `getAccountInfo()` hits a 404 path.

Purpose: a previous attempt to fix this (docblock dated 2026-07-23) put `priority` in the right VALUE but the wrong LOCATION in the JSON, and shipped undetected because the existing tests only asserted against the same wrong location. This plan corrects the payload shape, updates tests to assert the correct root-level structure (so this exact class of regression cannot recur silently), and — critically — verifies the fix against Hablame's REAL API (not just mocks), since that is exactly where the previous fix's flaw was invisible.

Output:
- app/Services/HablameSmsService.php — sendRaw()/send() emit root-level `priority`/`from`; getAccountInfo() uses the corrected route; outgoing payload is logged for future debuggability.
- tests/Feature/HablameSmsServiceTest.php + tests/Feature/OtpVerificationServiceTest.php — assertions rewritten to check the payload ROOT.
- A real, live-API verification run (real SMS to 3043978157 + real account-info call + message-status polling) proving the fix works outside of mocks.
</objective>

<interfaces>
Current (buggy) structure in app/Services/HablameSmsService.php — for reference, DO NOT copy this shape:

```php
// sendRaw() — priority nested INSIDE messages[0], wrong per Hablame docs
$messagePayload = ['to' => $formattedPhone, 'text' => $text];
if ($priority) {
    $messagePayload['priority'] = true; // WRONG: must be root-level
}
->post("{$this->apiUrl}/sms/v5/send", ['messages' => [$messagePayload]]);

// send() — 'from' never included anywhere
->post("{$this->apiUrl}/sms/v5/send", ['messages' => [['to' => $phone, 'text' => $message->content]]]);

// getAccountInfo() — wrong path, 404s against the real API
->get("{$this->apiUrl}/v5/account/info");
```

Correct schema per docs.hablame.co/reference/envio-sms-post (confirmed by Hablame support chat and official docs): `priority`, `from`, `certificate`, `flash`, `sendDate`, `campaignName` are all ROOT-level fields, siblings of `messages`:
```json
{
  "priority": true,
  "from": "SIGMA",
  "messages": [{ "to": "3001234567", "text": "..." }]
}
```
`certificate`/`flash` have accepted API-side defaults and are NOT required by this fix — only `priority`/`from` placement and the `getAccountInfo()` route are broken; do not add certificate/flash keys.

Class properties already available (constructor already sets these, `from` is currently a dead property never used in any payload):
```php
protected ?string $apiKey;   // config('services.hablame.api_key')
protected string $apiUrl;    // config('services.hablame.api_url')
protected string $from;      // config('services.hablame.from'), default 'SIGMA'
protected bool $sandboxMode; // config('services.hablame.sandbox_mode', false)
```

Existing tests currently assert the WRONG (nested) structure and must be corrected, not just re-run:
- tests/Feature/HablameSmsServiceTest.php: "sendRaw posts a priority true message when priority is requested" and "sendRaw does not include a priority key when priority is false" both currently check `$body['messages'][0]['priority']` — change to `$body['priority']` (root).
- tests/Feature/HablameSmsServiceTest.php: "can get real account info" fakes `'*/v5/account/info'` — change to `'*/account/v5/info'`.
- tests/Feature/OtpVerificationServiceTest.php: "generate sends the otp via HablameSmsService::sendRaw with priority true..." checks `$body['messages'][0]['priority']` — change to `$body['priority']`.

OtpVerificationService::generate() calls `$this->sms->sendRaw($phone, $message, priority: true)` — this call site is NOT modified by this plan (out of scope per bug context); only what sendRaw() does internally with `priority` changes.
