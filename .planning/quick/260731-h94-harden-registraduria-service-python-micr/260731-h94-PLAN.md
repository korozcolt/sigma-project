<objective>
Harden `registraduria-service/app.py` for production concurrency by replacing Flask's built-in Werkzeug development server (`app.run(...)`, the last line of the file) with `waitress`, a mature, pure-Python, single-process/multi-threaded production WSGI server — without changing the app's in-memory session-sharing model in any way.

**Why this shape, not gunicorn multi-worker:** the app's `sessions: dict = {}` (module-level, `sessions_lock`-guarded) has NO external backing store. A `POST /lookup*` and a later `GET /result/<id>` for the same session MUST land on the exact same OS process or the session silently 404s. Waitress's model is single-process with an internal thread pool — it never forks/spawns multiple OS processes — which is the only concurrency model compatible with this app's existing design, and it mirrors the app's own existing `threading.Thread(...).start()` pattern for background lookups exactly. Gunicorn was considered as a fallback (`--workers 1 --threads 8 --worker-class gthread`) but is unnecessary: waitress is a simpler drop-in for a pure-Flask app with no gunicorn-specific features needed, requires zero Dockerfile change (unlike the gunicorn fallback, which would require rewriting the CMD), and was confirmed installable and working under this project's exact Python version (3.14.3, via `registraduria-service/venv`) during this session's investigation.

**Confirmed no asyncio conflict:** each Flask route handler (`lookup()`, `lookup_infovotantes()`, `lookup_censo()`) only ever calls `threading.Thread(target=_run*, daemon=True).start()` and returns immediately — the route handler itself (which is what any WSGI server's worker thread actually executes) never calls `asyncio.run()`. `asyncio.run()` only runs inside the newly spawned daemon thread, entirely decoupled from whichever thread waitress used to serve the HTTP request. There is no shared-event-loop conflict regardless of which WSGI server is used.

Purpose: eliminate the load-dependent/intermittent request failures observed today (a live Jam.dev session showed 15 consecutive 503s from Laravel's proxy to this service during an in-progress 2captcha lookup) — the third and final production-readiness fix requested today (after 260731-ezk and 260731-g7h).

Output: `registraduria-service/app.py` boots via waitress instead of Werkzeug's dev server; `registraduria-service/requirements.txt` gains the `waitress` dependency; a documented, real concurrent-load manual verification proving the fix works.
</objective>
