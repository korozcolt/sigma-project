<objective>
Fix a confirmed critical security/data-leak bug in production: coordinators (same role, same municipio, same campaña) can see/export/act on leaders (and by extension, apoyos) belonging to ANOTHER coordinator, because 4 authorization checks compare role + municipio + campaña shared, but never compare `coordinator_user_id`. This diagnosis is already confirmed from a prior investigation in this conversation — no re-investigation needed, only implementation.

The 4 exact fixes:
1. `app/Http/Controllers/Coordinator/LeadersExportController.php` — export query never filters by `coordinator_user_id` (most severe: bulk PII export).
2. `resources/views/livewire/coordinator/leader-add-voter.blade.php` `mount()` — write path, missing `coordinator_user_id` check (copied the pre-existing bug from fix 3 in commit c09f89d).
3. `resources/views/livewire/coordinator/leader-voters.blade.php` `mount()` — read path, original bug.
4. `app/Exports/TopLeadersExport.php` `query()` — rebuilds its own query without the `coordinator_user_id` filter that the on-screen `TopLeadersTable` widget already applies correctly.

Every fix ships with a Pest test for the specific gap that was never covered before: SAME municipio + SAME campaña + DIFFERENT `coordinator_user_id` (not the already-covered "different municipio" case).

Purpose: Stop cross-coordinator PII leakage in production — a coordinator must never see, export, or write apoyos for another coordinator's leaders.
Output: 4 authorization fixes + 4 sets of regression tests (2 extended existing files, 2 new test files) proving the real production gap is closed.
</objective>
