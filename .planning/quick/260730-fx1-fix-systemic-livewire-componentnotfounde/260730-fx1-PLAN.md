<objective>
Fix the systemic version of the `Livewire\Exceptions\ComponentNotFoundException` bug already diagnosed and fixed once for `RevalidationProgressWidget` (commit `236ca78`, see `.planning/STATE.md`). The SAME root cause affects every other page-scoped Filament widget (attached via a Page's `getHeaderWidgets()`/`getFooterWidgets()`, not the panel's global `->widgets([...])` array): `CallCenterStatsOverview`, `CallQueueTable`, `CallHistoryTable` (Call Center page) and `DiaDStatsOverview`, `DiaDTerritorialProgressTable` (Día D page). All 5 are currently unregistered and will throw the same exception on their first `wire:poll` follow-up request in production.

Consolidate the existing single-widget registration workaround plus these 5 newly-identified widgets into ONE mechanism — a small array of page-scoped widget classes + a loop computing each class's deterministic alias via `Livewire\Mechanisms\ComponentRegistry::getName()` and registering it with `Livewire::component()` — instead of 6 near-duplicate hardcoded calls.

Purpose: Prevent a repeat of the exact incident already reported by direct user feedback — a prior deploy of this same bug class (the original `RevalidationProgressWidget` fix) went out without browser verification and broke production. This plan closes the remaining 5 known instances AND makes future page-scoped widgets easy to register correctly (append one class to the array) instead of copy-pasting a raw `Livewire::component()` call.
Output: Consolidated registration in `AppServiceProvider::boot()`, a Pest regression test proving all 6 aliases resolve, and mandatory real-browser verification of both affected pages (`/admin/call-center`, `/admin/dia-d`) before this is considered done.
</objective>
