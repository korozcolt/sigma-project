# Quick Task 260726-k80: Fix PollingPlaceResolver Hardcoded max_tables Summary

**`resolveOrCreatePollingPlace()` now derives `max_tables` from the real `mesa_numero` (create and bump-on-match), fixing the validation rule that silently rejected every Registraduría-autofilled mesa — including the local "IE SAN JOSE C I P" (id=2) record, corrected in the live dev DB to `max_tables = 13`.**

## Performance

- **Duration:** ~20 min
- **Tasks:** 2 (TDD create/bump fix + local data correction)
- **Files modified:** 2

## Accomplishments

- `resolveOrCreatePollingPlace()` computes `$mesaNumero`/`$maxTablesFromMesa` once from `$fields['mesa_numero']` and uses it in both branches:
  - DIVIPOLE-code branch: explicit find-then-create replaces `firstOrCreate()` — a found match gets bumped (`update(['max_tables' => $maxTablesFromMesa])`) only if the incoming mesa exceeds its current value; a new record is created with `max_tables` set from mesa instead of hardcoded `0`.
  - Name-match branch: same find-then-bump-then-return / else-create pattern replaces the `?? PollingPlace::create(...)` one-liner.
- Legacy behavior fully preserved when `mesa_numero` is absent/blank — new records still get `max_tables = 0`.
- 5 new Pest tests (Test 27-31) lock in: create-with-mesa on both branches, bump-on-match, no-downgrade-on-match, no-mesa-numero-unchanged. Followed strict TDD: tests written and confirmed RED first (3 of 5 failed as expected, 2 already passed confirming no accidental behavior change), then the fix made all 33 tests in the file GREEN.
- Local dev DB data fix applied for real via `php artisan tinker`: `PollingPlace` id=2 ("IE SAN JOSE C I P") `max_tables` bumped from `0` to `13` (matching `registraduria_lookups` document_number `1102812122`'s `mesa_numero = "13"`).
