- **`PollingPlaceResolver::startLiveLookup()` (`app/Services/PollingPlaceResolver.php`, ~line 41-50) does not fall through to the next live adapter when a reachable adapter's `startLookup()` call itself throws.** The method loops `$this->liveAdapters` and, for the FIRST adapter where `isReachable()` is true, calls `$adapter->startLookup($cedula)` and returns/throws immediately — unlike the sibling `isLiveReachable()` just above it, which cheaply probes ALL adapters' `isReachable()` with no side effects. The two diverge because `isReachable()` probes the real EXTERNAL Registraduría-hosted site (`config('services.consulta_censo.probe_url')`) while `startLookup()` calls the INTERNAL Python microservice proxy (`config('services.consulta_censo.url')`, e.g. `http://sigma-registraduria:5757/lookup/censo`) — a different network path, so an adapter can be "reachable" while its internal proxy path is broken. This caused a real incident in sigma-betha production on 2026-07-31: after deploying quick tasks 260731-ezk through 260731-i5g (added `ConsultaCensoService` as a 3rd live adapter + config fallback), the separate `sigma-registraduria` Dokploy service (autoDeploy=false) had not yet been redeployed with the new `/lookup/censo` route — its external probe was up so `isReachable()` returned true, `startLiveLookup()` committed to `ConsultaCensoService::startLookup()`, which 404'd against the internal proxy and threw, uncaught all the way up through `HasRegistraduriaPolling::openRegistraduriaBrowser()`'s outer try/catch (which only shows a hard "Error al conectar con el servicio" notification and never reaches the DB-reconstruction/national-snapshot fallback tiers, gated behind `isLiveReachable()`, which was true). Confirmed via `storage/logs/laravel.log`: 8 "ConsultaCensoService: lookup failed" 404 entries for real cédulas, resolved by manually redeploying `sigma-registraduria` (rebuilt image from git checkout at `/etc/dokploy/applications/sigma-registraduria/code/registraduria-service`, verified in an isolated test container, tagged the prior image `sigma-registraduria:rollback-260731` for rollback safety, then `docker service update --force --image sigma-registraduria:latest sigma-registraduria`) — this fixed the SYMPTOM, not the underlying code gap. Not adapter-specific: the same class of bug exists for `InfovotantesService` and `RegistraduriaService` — any adapter whose external probe_url and internal service_url are decoupled. **Recommended future fix (not yet implemented):** `startLiveLookup()` should catch a `startLookup()` failure on one adapter and continue trying the next reachable adapter (bounded) before finally throwing, mirroring the resilience `attemptLiveAutomated()` already has for the automated/headless cascade (covered by `PollingPlaceResolverPriorityTest`) — this would make the interactive modal path (`openRegistraduriaBrowser`/`forceRefreshFromRegistraduria`) as resilient as the automated path already is.
