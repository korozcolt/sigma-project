# Phase 05.1 Plan 06: Ownership-Scoped Coordinator/Leader Dashboard Widgets Summary

**Coordinator and Leader panel widgets (TopLeadersTable, CampaignStatsOverview, TerritorialDistributionChart, ValidationProgressChart) now scope by team/own-registered-voter ownership via explicit `Auth::id()`/`hasRole()` branches, closing REPT-03 — previously every one of them scoped by campaign only, identical to what an admin sees.**

## Performance

- **Duration:** ~55 min (majority spent diagnosing a pre-existing worktree environment issue, not plan logic)
- **Tasks:** 3
- **Files modified:** 4 widget classes + 1 new test file

## Accomplishments
- A coordinator's `TopLeadersTable` now ranks only their own assigned leaders (`coordinator_user_id = Auth::id()`), not every leader in the campaign
- A leader's `CampaignStatsOverview`/`ValidationProgressChart`/`TerritorialDistributionChart` show only their own registered voters (`registered_by = Auth::id()`)
- A coordinator's same 3 widgets show only their team's voters (`registered_by IN coordinator's leaders`)
- Admin view of all 4 widgets is completely unaffected — still campaign-wide, unrestricted
- New `tests/Feature/OwnershipScopedWidgetsTest.php` proves coordinator-scoped, leader-scoped, and admin-unrestricted behavior across both `TopLeadersTable` and `CampaignStatsOverview`

**Plan metadata:** committed as part of this summary commit.

## Files Created/Modified
- `app/Filament/Widgets/TopLeadersTable.php` - Adds a coordinator-scoping `when()` branch to the ranking query; unchanged for admin
- `app/Filament/Widgets/CampaignStatsOverview.php` - Adds `scopedVoterQuery(Campaign): Builder` private helper used by all 4 stat methods + both mini-charts; leader/coordinator branches added to `getActiveLeadersStat()`
- `app/Filament/Widgets/TerritorialDistributionChart.php` - Adds inline `->when(hasRole(LEADER)/hasRole(COORDINATOR))` branches to the municipality-distribution query
- `app/Filament/Widgets/ValidationProgressChart.php` - Adds the same `scopedVoterQuery(Campaign): Builder` helper (duplicated per phase's explicit-over-abstraction preference), used inside the 30-day loop
- `tests/Feature/OwnershipScopedWidgetsTest.php` - New: 2 coordinators x 2 leaders x distinct voter counts fixture; 5 tests covering coordinator/admin `TopLeadersTable` scoping and leader/coordinator/admin `CampaignStatsOverview` scoping

## Decisions Made
- Mirrored the existing `CallCenterStatsOverview::getStats()` `Auth::id()`-into-query pattern exactly, per the plan's interface contract — no generic polymorphic scope resolver was introduced (per research recommendation: only 4 widgets need this)
- For `CampaignStatsOverview::getActiveLeadersStat()`, replaced the leader-role branch's stat entirely (a leader has no leaders to rank) with "Mis Apoyos Registrados" per the plan's explicit instruction, rather than showing a zero/empty "Líderes Activos" stat
- `TerritorialDistributionChart` intentionally does not use a `scopedVoterQuery()` helper (its query is a raw join/select shape, not a plain `Voter::where(...)` builder) — the plan explicitly allowed inline `hasRole()` scoping as an equivalent alternative here
- Regression test switched from `assertSeeHtml`/`assertDontSeeHtml` (raw HTML substring match) to `assertSeeText`/`assertDontSeeText` (tag-stripped) after discovering the raw HTML approach produced false negatives/positives: the campaign-total digit sequence coincidentally appeared inside `wire:snapshot` checksum hex and inside unrelated SVG `<path d="...">` numeric data, which a plain substring search over the full HTML dump could not distinguish from the actual rendered stat value

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Worktree had no independent `vendor/`, no `.env`, and no built frontend assets**
- **Found during:** Task 1, first attempt to run `php artisan test --filter=OwnershipScopedWidgetsTest`
- **Issue:** This worktree (`agent-a7dded664cebd4c0d`) had neither a `vendor/` directory nor a `.env` file. A symlinked `vendor/` (mirroring a sibling worktree's setup, itself pointing at the main repo's `vendor/`) caused every Feature-suite test to silently fail to bind `Tests\TestCase` (Pest's `pest()->extend(...)->in('Feature')` directory-matching broke under macOS/`/Volumes` realpath resolution through the symlink), surfacing as `Call to undefined method ...::artisan()` / `Target class [config] does not exist` even on unrelated, unmodified pre-existing test files (confirmed via `CoordinatorLeaderRelationshipTest`, which passed fine in the main repo but failed identically in this worktree before the fix)
- **Fix:** Ran an independent `composer install` (real `vendor/`, not a symlink) plus copied a `.env` from a sibling worktree (`DB_CONNECTION` only matters for `.env`; tests use `phpunit.xml`'s `sqlite :memory:` override regardless) and ran `npm run build` (symlinked `node_modules` to the main repo's, built via `vite build`) to eliminate unrelated `Vite manifest not found` failures across ~20 full-page tests unrelated to this plan
- **Files modified:** None tracked in git (`vendor/`, `.env`, `node_modules`, `public/build/` are all gitignored); no application code touched by this fix
- **Verification:** `php artisan test --filter=CoordinatorLeaderRelationshipTest` (pre-existing, unmodified test) went from failing to passing after the fix; full `composer test` then ran cleanly modulo one known pre-existing flake (see below)
