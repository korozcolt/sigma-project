<decisions>
## Implementation Decisions

### Do not touch (already COVERED — verified by direct code read + passing tests)
- Campaign context switcher, `CampaignContextScope` global scope on 13 models, `CampaignMembershipScope`, write-time `campaign_id` enforcement (`HasCampaignContext`), `Campaign.scope`/territory columns with self-consistent nullification (CAMP-01..04).
- 3-panel RBAC (Admin/Coordinator/Leader), `User::canAccessPanel()`, `EnsureFilamentAccess` (PERM-01).
- Voter creation/import isolation, territorial assignment (cascading department→municipality→neighborhood→polling_place), Registraduría polling-place lookup (VOTE-01, VOTE-02).
- Single `VoterStatus` enum as canonical status source across imports/validation/dashboards/Day D; `ValidationHistory` audit trail (VOTE-05).
- `CallAssignment`/`VerificationCall`/`SurveyResponse` relations and traceability, `CallAssignmentService` anti-duplicate mechanism (OUTR-02, OUTR-03 fully; OUTR-01/05 mechanism exists — see gaps below for the missing *test*).
- `Message` full lifecycle tracking (status/sent_at/delivered_at/batch_id) — audit trail itself is fine, only the status *classification* has a bug (see OUTR-04 gap).
- All 6 Phase-04.1 report widgets/exports reconcile to campaign-scoped source data, `DuplicatesReportTable`/`DuplicatesExport` is the sole intentional cross-campaign exception (REPT-01).
- `DiaD` page (voter lookup, evidence-gated vote marking with photo+GPS), `VoteRecord` model with full audit metadata, `DiaDStatsOverview` live widget, `FinalizeElectionEvent` job, ~15 Day D test files (DAYD-01, DAYD-02, DAYD-05).

### What this phase must actually build/fix

**Phase 1 gaps:**
- **PERM-02**: Denial messages are generic (`EnsureUserHasRole.php:32` → `abort(403, 'No tienes permiso...')`; `CampaignContext.php:125` generic `RuntimeException`). `bootstrap/app.php` `withExceptions()` is empty. Need reason-specific messaging distinguishing campaign-scope vs role vs territorial-ownership denial.
- **PERM-03**: Voter→registrant ownership is visible (`VotersTable.php:110`), but there's no single consolidated "who owns this territory / follow-up queue" view — it's scattered across widgets (`TopLeadersTable`, `TopCoordinatorsTable`, `TerritorialAssignment`).
- **CAMP-05**: Latent risk, not an active leak — `CampaignContextScope` becomes a silent no-op when there's no `Auth::user()` (queue context). Nothing today relies on the implicit scope inside a job (all queue queries filter explicitly), but audit the 3 `withoutGlobalScopes()` call sites in `VoterResource.php:69`, `SurveyResource.php:65`, `CampaignResource.php:80` to confirm each re-applies an explicit campaign filter.
- **OTP (client request, no formal REQ-ID)**: Nothing exists — no code generation/storage/verification, no wiring into leader registration. Must be parameterizable per campaign (message text stored in `Campaign.settings`, per client request captured 2026-07-23 in `.planning/notes/2026-07-23-requisito-nuevo-feature-pendiente.md`). **Hablame support confirmed the delivery fix**: add `"priority": true` to each message in the `POST /sms/v5/send` body — no sender-ID registration or certified-product contract needed.
- **Kill switch (client request, no formal REQ-ID)**: Nothing exists (`grep` for `maintenance`/`killswitch`/`::down(` across `app/`+`routes/` → zero hits). Build on Laravel's native maintenance mode via a Filament action, with automatic bypass for the super admin role.

**Phase 2 gaps:**
- **VOTE-03**: `VoterValidationService` and job `ValidateVoterAgainstCensus` exist (set `VERIFIED_CENSUS`/`REJECTED_CENSUS` + `census_validated_at`) but are dispatched from nowhere — no UI action wires them. The Registraduría lookup is a separate, already-wired mechanism (polling-place lookup, not census pass/fail) and does show source in notifications. Need: a UI action triggering census validation with a clear pass/fail + source display (`ValidationHistory.validation_type` is captured but never shown in the Voter UI).
- **VOTE-04**: No "what's missing / next recommended action" indicator anywhere. `ViewVoter` infolist is 8 static fields. `VoterStatus` enum descriptions partially substitute but aren't framed as guidance.
- **VOTE-06**: `VotersTable.php:151-188` filters status/municipality/neighborhood/registered_by/campaign/trashed — all campaign-safe. Missing: a contact-state filter (open call assignment / survey completed) — would need to join `verificationCalls`/`surveyResponses`.

**Phase 3 gaps:**
- **OUTR-01**: Campaign isolation for the call queue is real (`CallAssignment` uses `HasCampaignContext`, `CallAssignmentService::forCampaign()` throughout) but has zero dedicated cross-campaign-leakage regression test.
- **OUTR-04 — confirmed live bug (2026-07-23)**: `HablameSmsService::send()` only recognizes Hablame `statusId` 102/106 as success. A real test send today returned `statusId: 1` ("processing") and was misclassified as `failed` even though Hablame's own `GET /api/sms/v5/message/{id}` endpoint later confirmed real delivery progress (`messageStatus: 2`, operator-delivered). Fix the status mapping (treat 1/processing as pending, not failed) — optionally poll the query endpoint for final status instead of trusting the synchronous send response alone.
- **OUTR-05**: `CallAssignmentService::loadBatchForCaller()` already excludes voters with an existing pending/in-progress assignment and voters past 3 attempts (real logic, not a stub) — but has no dedicated regression test asserting "does not create duplicate assignment for voter with existing pending assignment."

**Phase 4 gaps:**
- **REPT-02**: Voter progress + validation progress widgets exist (`CampaignStatsOverview`, `ValidationProgressChart`). Day D readiness exists as a *live tracking* widget (`DiaDStatsOverview`, on the DiaD page, not a dashboard) rather than a pre-day readiness checklist — acceptable as-is per DAYD-04 note below. **Missing:** no follow-up/validation backlog count indicator anywhere (grepped `backlog`/`pendiente`/`seguimiento` across all widgets — zero hits).
- **REPT-03 — biggest gap in this phase**: `CoordinatorPanelProvider.php` and `LeaderPanelProvider.php` register real widgets (`CampaignStatsOverview`, `TerritorialDistributionChart`, `TopLeadersTable`/`ValidationProgressChart`) — panels are NOT admin-only as previously assumed. But every one of those widgets scopes by campaign only, identical to what admin sees — **zero ownership/territory scoping**. A coordinator's `TopLeadersTable` ranks ALL leaders in the campaign, not just their own team. Only the call-center widgets (`CallCenterStatsOverview`, `CallHistoryTable`, `CallQueueTable`) scope by `Auth::id()`. This phase must add ownership-scoped variants (coordinator sees only their assigned leaders' rollup; leader sees only their own territory/voters).
- **REPT-04**: Zero drill-through anywhere. Only 2 `->url()` widget links exist system-wide (`BirthdayWidget.php:96` → message-create; `CallQueueTable.php` → claim-call row action), neither is aggregate→filtered-list drill-through. Add click-through from at least the highest-value KPI/ranking widgets to their underlying filtered Voter/report table.

**Phase 5 gaps:**
- **DAYD-03**: Duplicate-vote guard is application-level only (`DiaD.php:198-210`, `VoteRecord::where('voter_id')->where('election_event_id')->first()`) — no DB unique index on `(voter_id, election_event_id)`, so concurrent requests can race past the check. Also no "conflict" handling: `markDidNotVote()` doesn't check for/remove an existing evidence-backed `VoteRecord` for that voter+event, so a voter could end up `DID_NOT_VOTE` while a photo-backed vote record still exists. Add the DB unique constraint (migration) and define+enforce the conflict rule.
- **DAYD-04**: `DiaDStatsOverview` shows campaign-level totals only (total/confirmed/voted/didNotVote/participation %, 10s polling) — no breakdown by municipality/polling place/leader/coordinator as the requirement asks ("by campaign and relevant territory"). Add a territory dimension.
- **QUAL-01**: Day D evidence integrity is well-tested overall (`VoteRecordTest`, `DiaDEvidenceTest`, `DiaDGpsValidationTest`, `DiaDComponentTest`, `ElectionEventClosureTest`, `DiaDWidgetIntegrationTest`, E2E Chrome tests) BUT: `FinalizeElectionEvent` job itself is never directly tested — `ElectionEventClosureTest.php:58-76` reimplements the closure query inline instead of dispatching the real job. No test asserts DB-level duplicate prevention (there is none yet — depends on DAYD-03's fix). Add a direct job-dispatch test and a DB-level duplicate-prevention test.
- **QUAL-02 — biggest gap in this phase**: Zero proactive observability on the Day D path. No `Log::` calls anywhere in `DiaD.php`, `FinalizeElectionEvent.php`, `VoteRecord`, `ElectionEvent` (e.g. a photo-save failure at `DiaD.php:225` is shown to the user but never logged). `FinalizeElectionEvent` is dispatched via `dispatchSync()` (`ManageElectionEvents.php:264`), bypassing the queue entirely — a failure throws inline, never lands in `failed_jobs`, no retry, no alert path. No Horizon/Telescope/Sentry/health-check anywhere in `composer.json`. Add structured logging on the Day D + closure paths, dispatch `FinalizeElectionEvent` through the real queue (or otherwise capture/alert on failure), and add at minimum `failed_jobs` visibility.

### Claude's Discretion
- Exact UI treatment for PERM-02's reason-specific denial messages (custom exception classes vs a shared "why blocked" helper).
- Whether the OTP feature's code-generation/expiry/retry logic lives in `HablameSmsService` directly or a new dedicated service — CLAUDE.md's project conventions (thin controllers, Actions/Services with `handle()`/`execute()`) should guide this.
- Exact drill-through mechanism for REPT-04 (Filament `->url()` on stat cards vs table row actions) — pick whichever fits each specific widget best; doesn't need to be uniform across all of them.
- Scope of REPT-03's ownership-filtering: whether to add new dedicated Coordinator/Leader-only widget classes or parameterize the existing admin widgets with a scope toggle. Given CAMP-05's queue-context finding, prefer explicit `Auth::id()`-based scoping (mirroring the existing `CallCenterStatsOverview` pattern) over relying on any implicit global scope.

</decisions>
