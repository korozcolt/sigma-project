## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Cross-campaign duplicate detection returned duplicate_sequence 0 instead of incrementing, causing a UNIQUE constraint violation**
- **Found during:** Task 3, while writing the "existing cedula creates a duplicate" test
- **Issue:** `VoterDuplicateAssignmentService::nextSequenceFor()` queried `Voter::withTrashed()->where('document_number', ...)->max('duplicate_sequence')`. Since `Voter` uses `HasCampaignContext` (adds a campaign-scoped global scope to every query), this lookup silently only considered voters in the *current* campaign context, returning `null`/`0` for a document_number that already existed under a different campaign. The DB's `(document_number, duplicate_sequence)` unique constraint is intentionally global (per the 2026_01_19 migration), so this produced a real `UNIQUE constraint violation` on insert whenever a duplicate cedula was registered under a different campaign than the first occurrence — exactly the case D-06/CSV import needs to handle gracefully.
- **Fix:** Added `Voter::withoutGlobalScopes()` to the lookup query in `nextSequenceFor()`, since duplicate-sequence assignment must consider ALL voters system-wide, not just the current campaign's.
- **Files modified:** `app/Services/VoterDuplicateAssignmentService.php`
- **Verification:** New test "a row whose cedula already exists creates a duplicate Voter with incremented sequence and DUPLICATE status" passes; re-ran `ApoyoDuplicateSequenceTest`, `VoterResourceTest`, `VoterTest`, `VoterDuplicateReportTest` (all pre-existing duplicate-related suites) — all still green.
- **Committed in:** `7c4d0f4` (part of Task 3 commit)
