# Phase 02.1 Plan 11: Real Ownership Transfer for Duplicate Reassignment Summary

**Rewrote the "Reasignar dueño de duplicado" Filament action so it transfers `registered_by` to an admin-selected leader/coordinator (restricted server-side to actual co-registrants of the disputed cédula) and explicitly demotes every other sibling row to DUPLICATE, closing the UAT-confirmed gap between the client's literal requirement and the narrower flag-clearing behavior shipped in plans 02.1-08/09.**

## Accomplishments
- `VoterDuplicateAssignmentService::siblingsFor(string $documentNumber)` added — cross-campaign-safe lookup (`withoutGlobalScopes()->withTrashed()`, ordered by `duplicate_sequence`) of every Voter row sharing a document_number, mirroring the existing `nextSequenceFor()` pattern
- `EditVoter::getHeaderActions()`'s `reassignDuplicateOwner` action rewritten: form now includes a `new_owner_user_id` Select (options + `Rule::in()` validation both restricted to actual sibling `registered_by` values) alongside the existing mandatory `notes` Textarea
- Action now runs a `DB::transaction` over every sibling: the chosen winner gets `status = PENDING_REVIEW` and `registered_by` set to the selection; every other sibling gets `status = DUPLICATE`; every sibling gets its own `ValidationHistory` row (`validation_type = duplicate_reassignment`)
- `duplicate_sequence` is never written anywhere in `EditVoter.php` — D-10 immutability confirmed structurally and by test
- `ApoyoDuplicateSequenceTest.php` extended from 8 to 11 tests: kept the 3 sequence-assignment and 3 visibility tests verbatim, replaced the 2 old reassignment tests with 5 covering ownership transfer, mandatory-note enforcement, no-op winner immutability, invalid-owner rejection, and sequence immutability under an actual ownership flip
- `docs/REGLAS_NEGOCIO.md` synced to describe the real ownership-transfer semantics instead of the old narrower flag-clearing description
- `.planning/.../02.1-HUMAN-UAT.md` updated: status `diagnosed` → `resolved`, Gap 1 marked resolved, summary counts updated to `passed: 1`, `issues: 0`

## Decisions Made
- All sibling rows (not just the currently-edited record) are updated transactionally in one action call, and each gets its own audit row — this was necessary to satisfy the "every non-chosen sibling row ends up DUPLICATE" and "every sibling gets its own validation_histories row" must-haves.
- No new database columns or schema changes were needed — `registered_by` was already a NOT-NULL FK on `voters`, so this was a pure application-layer change (Rule 1/2 territory, no Rule 4 architectural escalation required).
