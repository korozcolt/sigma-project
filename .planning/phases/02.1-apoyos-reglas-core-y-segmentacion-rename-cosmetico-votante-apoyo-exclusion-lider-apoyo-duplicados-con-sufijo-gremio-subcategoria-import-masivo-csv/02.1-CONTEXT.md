<decisions>
## Implementation Decisions

### Alcance del rename Votante→Apoyo
- **D-01:** "Apoyo" reemplaza "Votante" en TODA la UI, siempre — navegación, formularios, reportes, exports, notificaciones. Sin excepción para pantallas de censo/Registraduría; un solo término en todo el sistema.

### Duplicados — UX y auditoría
- **D-02:** Alerta explícita antes de guardar cuando la cédula ya existe: el formulario debe avisar que se creará como duplicado en disputa y pedir confirmación del operador antes de guardar. No es un guardado silencioso.
- **D-03:** La reasignación de dueño de un duplicado por un admin requiere nota/motivo obligatorio (texto libre), además del registro automático de quién y cuándo — auditoría completa para sostener el "debate interno" que menciona el cliente.

### Modelo de Gremio/Subcategoría
- **D-04:** Jerárquico — cada Subcategoría pertenece a un Gremio específico. Debe ser catálogo administrable desde Filament (CRUD), no un enum fijo en código, porque el catálogo va a crecer. El formulario pide primero Gremio, luego filtra Subcategoría según ese gremio.
- **D-05:** Ambos campos son opcionales siempre — tanto para apoyos nuevos (formulario e import) como para los existentes. No se fuerza clasificación retroactiva ni se bloquea el registro si aún no se conoce el dato.

### Import masivo CSV
- **D-06:** Procesar las filas válidas y generar un reporte descargable de filas rechazadas con el motivo del rechazo — no se aborta el archivo completo por un error puntual (ej. cédula de un líder, dato inválido).
- **D-07:** Solo Admin de campaña / Super Admin puede ejecutar el import masivo — no delegado a coordinadores en esta fase.

### Resueltas tras research (RESEARCH.md 02.1)
- **D-08:** La regla de exclusión líder-apoyo aplica SOLO a roles `leader` y `coordinator` — no a `admin_campaign`. Importante: `UserObserver::created()` ya auto-crea un `Voter` vinculado (`voters.user_id`) para todo `User` con document_number/municipality/campaign, incluidos líderes y coordinadores (ver `tests/Feature/UserVoterRelationTest.php`). La nueva regla de exclusión debe convivir con ese registro de sistema existente — no bloquearlo — y solo impedir que un líder/coordinador aparezca como Apoyo de OTRO líder/coordinador.
- **D-09:** Los catálogos Gremio y Subcategoría son GLOBALES, compartidos entre todas las campañas — mismo patrón que `Department`→`Municipality` hoy (no hay scope por campaña en esos catálogos).
- **D-10:** Al reasignar el dueño de un duplicado, el `duplicate_sequence` (sufijo -0/-1/-2) queda INMUTABLE para siempre como identificador histórico. Reasignar solo cambia el estado (Asignado/Duplicado) y el líder dueño — no se renumeran sufijos.

### Claude's Discretion
- Copy exacto del mensaje de alerta de duplicado en el formulario.
- Diseño de la tabla del reporte de filas rechazadas del import.
- Estructura interna de las tablas catálogo Gremio/Subcategoría (nombres de columna, FK exacta).

</decisions>

## Specific Ideas

- Ejemplo del cliente para el esquema de sufijo: `1111111111-0`, `1111111111-1`, `1111111111-2` — el `-0` queda "Asignado" al primer líder que lo registró; los siguientes quedan en estado "Duplicado en disputa" hasta que un admin reasigne.
- Ejemplos de jerarquía Gremio → Subcategoría dados por el cliente: Manipulador de Alimentos → PAE, ESE; Mototaxista → Punto Éxito, Punto Guacarí.
