**Phase Goal:** Campaign operators work with "Apoyos" (not "Votantes") everywhere in the UI, leaders/coordinators cannot be registered as someone else's Apoyo, duplicate cedulas are tracked with an auditable suffix instead of blocked, Apoyos can be optionally classified by Gremio/Subcategoria, and admins can bulk-import Apoyos via CSV with a partial-success rejection report.

## Re-Verification Summary

The prior verification (2026-07-23, see history below) scored 10/10 must-haves but flagged D-03/D-10's "reassign duplicate owner" action as `human_needed`: the implementation only cleared a status flag on the single edited row and never touched `registered_by` (the field that actually names the owning leader), despite D-10's Spanish decision text literally describing changing "el líder dueño."

The user was asked to confirm intent and chose option (b): the client's original requirement explicitly said "reasignar... la propiedad de la cédula al otro Líder" (transfer ownership to the OTHER leader) — the narrower flag-clearing behavior does not satisfy this. A gap-closure plan (02.1-11, `gap_closure: true`) was planned, checked, executed, and its SUMMARY.md claims full resolution.

### What was re-verified (this pass)

1. **Read the actual current code** (not just the SUMMARY) for `VoterDuplicateAssignmentService::siblingsFor()` and `EditVoter::reassignDuplicateOwner`. Confirmed:
   - `siblingsFor(string $documentNumber)` returns every `Voter` row sharing that `document_number`, using `withoutGlobalScopes()->withTrashed()->orderBy('duplicate_sequence')` — cross-campaign-safe, mirroring the existing `nextSequenceFor()` pattern.
   - `reassignDuplicateOwner`'s form now includes a `Select::make('new_owner_user_id')` whose **options** are built from `$siblings->unique('registered_by')` (i.e., only leaders/coordinators who actually have a row for this cédula) and whose **validation** is independently enforced server-side via `->rule(Rule::in($ownerIds))` — not merely a UI-level filter. Confirmed by a passing test (`'rejects a new_owner_user_id that does not correspond to any sibling row registered_by'`) that submits an unrelated user id and asserts a form validation error.
   - The action's `DB::transaction` loop iterates **every** sibling row: the row whose `registered_by` matches the selected `new_owner_user_id` gets `status = PENDING_REVIEW` (and its `registered_by` is explicitly written in the `update()` call — an intentional, explicit assignment, not an accidental omission, even though its value is unchanged since the option is sourced from that same row); every other sibling gets `status = DUPLICATE`. This means a previously-"assigned" (-0, non-duplicate) row can be explicitly flipped to `DUPLICATE` if a different leader is chosen as the rightful owner — this is the real behavioral change from the prior implementation, and is exactly what was missing before.
   - `duplicate_sequence` is referenced only for display (the Select option label, e.g. "secuencia -1") and is never present as an `update()` key anywhere in the file — `grep -nE "duplicate_sequence['\"]?\s*(=>|=)" app/Filament/Resources/Voters/Pages/EditVoter.php` returns no matches. D-10 immutability holds structurally, not just by convention.
   - Every affected sibling row gets its own `ValidationHistory::create([...])` call with `validation_type = 'duplicate_reassignment'`, `validated_by = auth()->id()`, and the mandatory `notes` text (annotated per-row with whether it won or lost) — D-03's mandatory-note-audited-reassignment requirement now correctly extends to all affected rows, not just the one being edited.

   - Confirmed these are real Livewire/Filament pipeline executions with real `assertDatabaseHas`/`expect(...->fresh()...)` assertions against the actual database — not mocks or superficial stubs.
