# Phase 02.1: Apoyos - Reglas Core y Segmentación - Research

**Researched:** 2026-07-22
**Domain:** Laravel/Filament v4 brownfield hardening — schema migration (unique constraint replacement), cross-model validation, hierarchical catalogs, CSV import
**Confidence:** HIGH (all findings verified against actual repo code, not framework assumptions)

## Summary

This phase touches five distinct technical problems layered on top of the existing `Voter` model (cosmetically renamed to "Apoyo" in UI only). The codebase is small and consistent enough that every question in scope could be answered by reading actual files rather than guessing from training data — this research is almost entirely HIGH confidence because it is grounded in the real schema, real Filament v4.2.0 resources, and real Pest tests already in the repo.

The single most important finding is a **latent architectural conflict** the planner must resolve explicitly: `UserObserver::created()` already auto-creates a `Voter` record (via `voters.user_id`) for **every** `User` with a `document_number` + `municipality_id` + a campaign — this includes leaders, coordinators, and admin_campaign users. This is existing, intentional, tested behavior (`tests/Feature/UserVoterRelationTest.php`, `php artisan users:create-voter-records`). The new "líder no puede ser apoyo" exclusion rule must NOT break this self-record; it must instead prevent a *different, non-system* Apoyo record from being registered under a `document_number` that already belongs to a leader/coordinator user.

The second key finding is that **Filament v4 ships a native `ImportAction`/`Importer` system** (`filament/actions`, already installed, no new dependency) that natively satisfies D-06 (partial success + downloadable rejection report) and is a better fit than hand-rolling with `maatwebsite/excel`. It requires publishing three already-vendored migrations (queue batches, notifications, filament-actions), none of which exist in this project yet — this is a Wave 0 gap.

The third key finding is that the "duplicate with suffix" schema can be built with **one new integer column + a composite unique index**, reusing the existing `validation_histories` table for the mandatory reassignment audit trail (D-03) instead of creating new tables — this is the least-invasive option requested by CONTEXT.md's discretion note.

**Primary recommendation:** Add `voters.duplicate_sequence` (unsigned int, default 0) + composite unique (`document_number`, `duplicate_sequence`); add `VoterStatus::DUPLICATE`; reuse `validation_histories` (new `validation_type = 'duplicate_reassignment'`) for D-03 audit; use Filament's native `ImportAction`/`Importer` (not maatwebsite/excel) for the CSV import restricted to Admin/Super Admin; add a `DocumentNotBelongsToLeaderOrCoordinator` validation rule that explicitly excludes the record's own linked `user_id`.

### Pattern 1: Hierarchical Catalog (Gremio → Subcategoría), mirroring Department → Municipality

**What:** Two simple Eloquent models, parent/child via `belongsTo`/`hasMany`, each with its own Filament Resource for CRUD, no soft deletes, no campaign scoping (client examples — "Manipulador de Alimentos", "Mototaxista" — suggest these are **global** catalogs, not per-campaign; confirm with user only if ambiguity persists at plan time, otherwise default to global like `Department`/`Municipality`).

**When to use:** Any time a new optional classification catalog needs to grow over time without code changes — exactly the existing `Department`/`Municipality`/`Neighborhood` pattern already in this codebase.

**Example (mirrors `app/Models/Department.php` and `app/Models/Municipality.php` exactly):**
```php
// app/Models/Gremio.php — source: app/Models/Department.php (this repo)
class Gremio extends Model
{
    use HasFactory;

    protected $fillable = ['name'];

    public function subcategorias(): HasMany
    {
        return $this->hasMany(Subcategoria::class);
    }
}

// app/Models/Subcategoria.php — source: app/Models/Municipality.php (this repo)
class Subcategoria extends Model
{
    use HasFactory;

    protected $fillable = ['gremio_id', 'name'];

    public function gremio(): BelongsTo
    {
        return $this->belongsTo(Gremio::class);
    }
}
```

**Form cascading select** — mirrors the existing `department_id` → `municipality_id` cascading pattern already implemented in `VoterForm.php` (lines 268–304 of `app/Filament/Resources/Voters/Schemas/VoterForm.php`):

### Pattern 2: Duplicate-Cédula Schema — Recommended Approach

**Current state (must be reversed):**
- `2025_11_03_132954_create_voters_table.php`: original constraint was `unique(['campaign_id', 'document_number'])`.
- `2026_01_19_000001_make_voter_document_number_globally_unique.php`: dropped the composite unique, replaced it with `unique('document_number')` (bare, global, single-column).
- `VoterForm.php` lines 206–233: a `Rule::unique('voters', 'document_number')->whereNull('deleted_at')` plus a custom closure that inspects `withTrashed()` records and fails with campaign-aware messaging.
- `VoterResourceTest.php`: 2 tests assert this exact bare-unique behavior (`'document_number' => 'unique'` form error on both same-campaign and cross-campaign duplicate).
- `VoterTest.php`: 2 tests assert `Voter::factory()->create()` throws on duplicate `document_number` (model-level DB constraint).

**Recommended migration (new file, `xxxx_add_duplicate_sequence_to_voters_table.php`):**
```php
public function up(): void
{
    Schema::table('voters', function (Blueprint $table) {
        $table->unsignedInteger('duplicate_sequence')->default(0)->after('document_number');
    });

    // Backfill: all existing rows are currently globally unique, so they all get sequence 0 safely.
    Schema::table('voters', function (Blueprint $table) {
        $table->dropUnique(['document_number']); // reverses 2026_01_19_000001
        $table->unique(['document_number', 'duplicate_sequence']);
    });
}

public function down(): void
{
    Schema::table('voters', function (Blueprint $table) {
        $table->dropUnique(['document_number', 'duplicate_sequence']);
        $table->unique('document_number'); // restore prior state
        $table->dropColumn('duplicate_sequence');
    });
}
```

**Why this is the least-invasive option:**
- `document_number` itself stays untouched (pure cédula digits) — critical because it's used for census matching (`CensusImporter`), Registraduría lookups (`consultar_registraduria` action in `VoterForm.php`), phone/SMS matching, and searches (`->searchable()` on `document_number` in `VotersTable.php`). Literally storing `"1111111111-0"` in the column would break all of these.
- A `getDisplaySuffixAttribute()` accessor on `Voter` (e.g., `"{$this->document_number}-{$this->duplicate_sequence}"`) reproduces the client's example format (`1111111111-0`, `-1`, `-2`) for display only, with zero risk to existing integrations.
- Assignment logic: on create, compute `duplicate_sequence = Voter::withTrashed()->where('document_number', $value)->max('duplicate_sequence') + 1` (or `0` if none exist) inside a model `creating` event or a small `VoterDuplicateAssignmentService`. The first record for a cédula gets `0` ("Asignado"); every subsequent one gets an incrementing suffix and `VoterStatus::DUPLICATE` ("Duplicado en disputa" per client wording, D-02/D-03).
- `VoterStatus` gets one new case (ADR-005 compliant): `DUPLICATE = 'duplicate'` with Spanish label/color/icon/description following the exact existing `match()` pattern in `app/Enums/VoterStatus.php`.
- **D-02 (pre-save alert):** implement as a Filament form-level confirmation (e.g., a `->live()` check on `document_number` blur/change that queries for existing rows and shows a warning `Placeholder`/`Notification`, then requires the user to acknowledge before the `create()` action proceeds — e.g. a checkbox `Hidden`/`Toggle` gate, or a `requiresConfirmation()` wizard step). Exact copy is Claude's discretion per CONTEXT.md.
- **D-03 (reassignment audit):** reuse `validation_histories` — add a new `validation_type = 'duplicate_reassignment'` value (no schema change needed, column is already a free string), with `notes` made **required at the application layer** (the migration/model doesn't need it nullable→required change since Eloquent validation happens in the reassignment action's Form, not the DB column). A dedicated Filament `Action` on the Voter view/edit page (e.g., "Reasignar dueño de duplicado", visible only for `admin_campaign`/`super_admin` and only when `status === DUPLICATE`) should require a `Textarea` note and write both the `voters` status change and a `validation_histories` row (`validated_by` = `auth()->id()`, `created_at` = automatic).

**Rewriting existing tests (§8 of REGLAS_NEGOCIO.md, explicit CONTEXT.md instruction):**
- `tests/Feature/VoterTest.php`: `it('document_number is globally unique', ...)` and `it('document_number cannot be duplicated across different campaigns', ...)` — both currently assert `toThrow(Exception::class)`. These must become **positive** tests: creating a second Voter with the same `document_number` now succeeds and gets `duplicate_sequence = 1` and `status = DUPLICATE`; a genuinely-conflicting composite (`document_number` + `duplicate_sequence`) insert (bypassing the assignment service) is what should throw.
- `tests/Feature/Filament/VoterResourceTest.php`: `test('cannot create voter with duplicate document in same campaign', ...)` and `test('cannot create voter with duplicate document in different campaign', ...)` — both currently `assertHasFormErrors(['document_number' => 'unique'])`. These must become tests that assert the create **succeeds** but the resulting record is flagged as a duplicate (or, if D-02's confirmation gate is implemented as a required checkbox, that submission without acknowledging the checkbox produces a distinct validation error, while submission with acknowledgement succeeds as a duplicate).

### Pattern 3: Leader-Cannot-Be-Apoyo Validation — Interception Point

**Critical existing behavior that must NOT break** (`app/Observers/UserObserver.php`, `app/Models/User.php:111` `voter(): HasOne`, `voters.user_id` FK from `2025_11_08_231723_add_user_id_to_voters_table.php`):

Every `User::created()` event (in `UserObserver`) with a `document_number` + `municipality_id` + at least one campaign **already auto-creates its own linked `Voter` row** (`user_id` set, `status = CONFIRMED`, `registered_by = $user->id`). This is tested extensively in `tests/Feature/UserVoterRelationTest.php` and exists for **any** role with those fields populated (leader, coordinator, admin_campaign) — it is not itself the thing D-01's exclusion rule targets. `Voter::isSystemUser()` (`app/Models/Voter.php:149`) already distinguishes these "system" voter records, and `VotersTable.php` already renders a role badge for them.

**What the new exclusion rule must actually do:** prevent a leader from registering (via form or CSV import) a **separate, non-system** Apoyo record using a `document_number` that matches an existing `users.document_number` belonging to a user with role `leader`, `coordinator`, or (arguably) `admin_campaign` — while explicitly excluding the record's own linked system voter (`voter->user_id === $existingUser->id`) from tripping the rule.

**Recommended interception point:** a new `App\Rules\DocumentNotBelongsToLeaderOrCoordinator` `ValidationRule` class (mirrors the existing `MaxTablesForPollingPlace` style exactly — `implements ValidationRule`, constructor-injected context, single `validate()` method), invoked from the same `->rule()` closure block in `VoterForm.php` (lines 206–233) where the existing cross-campaign duplicate check already lives, so leader-exclusion and duplicate-detection share one code path. It must also be invoked from `ApoyoImporter::getColumns()`'s `cedula` `ImportColumn::rules()` for CSV import parity (D-06 requires rejected-with-reason CSV import rows for exactly this case — the client's own example is "cédula de un líder").

```php
// app/Rules/DocumentNotBelongsToLeaderOrCoordinator.php — mirrors app/Rules/MaxTablesForPollingPlace.php (this repo)
class DocumentNotBelongsToLeaderOrCoordinator implements ValidationRule
{
    public function __construct(private readonly ?int $excludeVoterId = null) {}

    public function validate(string $attribute, mixed $value, Closure $fail): void
    {
        $leaderOrCoordinator = User::query()
            ->role([UserRole::LEADER->value, UserRole::COORDINATOR->value])
            ->where('document_number', $value)
            ->first();

        if (! $leaderOrCoordinator) {
            return;
        }

        // Allow the user's own auto-created system voter record to pass through untouched.
        $isOwnSystemVoter = $this->excludeVoterId
            && Voter::whereKey($this->excludeVoterId)->where('user_id', $leaderOrCoordinator->id)->exists();

        if ($isOwnSystemVoter) {
            return;
        }

        $fail("Este documento pertenece a un líder/coordinador ({$leaderOrCoordinator->name}) y no puede registrarse como Apoyo.");
    }
}
```

**Open design question for the planner:** should `admin_campaign`/`super_admin` document numbers also be excluded from being registered as Apoyo? The client phrasing is "exclusión líder-apoyo" (leader-specific), but `UserObserver` auto-creates system voters for any role with the right fields. Recommend scoping the exclusion rule strictly to `leader`/`coordinator` roles (matching the phase name literally) unless the plan-check step surfaces a reason to broaden it.

### Pattern 4: ApoyosImport — Filament Native Importer (Recommended)

**What:** `Filament\Actions\Imports\Importer` subclass + `ImportAction` attached to `VotersTable`'s header actions, restricted via `->visible()`/`->authorize()` to `admin_campaign`/`super_admin` (D-07).

**Why this satisfies D-06 without custom code:** Per `vendor/filament/actions/docs/11-import.md` (read directly from the installed package, HIGH confidence): "If any rows fail validation, they will be compiled into a downloadable CSV for the user to review after the rest of the rows have been imported." This is exactly D-06's requirement, built in.

**Setup required (Wave 0 gap — none of these exist in this project yet):**

- **Hand-rolling a rejection-CSV importer with maatwebsite/excel** when Filament's native `ImportAction` already ships this exact feature as a first-class, already-installed capability.

## Common Pitfalls

### Pitfall 1: Breaking the UserObserver auto-voter flow
**What goes wrong:** A naive implementation of "leader cannot be apoyo" queries `users` for a `document_number` match and fails validation — but this also fires when the `UserObserver` itself calls `Voter::create()` for the user's own record, or when a leader edits their own linked voter record.
**Why it happens:** The exclusion rule and the auto-creation flow both touch the same `document_number` ↔ `users` relationship, from different code paths (`UserObserver::created()` uses `Voter::create()` directly, bypassing Filament form rules entirely — so it's actually safe from the Filament-side check; but if the rule is later moved to a model `saving` event, it would catch its own auto-creation and break `tests/Feature/UserVoterRelationTest.php`).
**How to avoid:** Keep the exclusion rule as a **Filament form / import-time only** validation rule class, not a global model `boot()` observer event, so `UserObserver`'s direct `Voter::create()` call remains unaffected. If the team later wants it at the model layer, it must explicitly exclude rows where `user_id` is being set to the matching user's own id.
**Warning signs:** `tests/Feature/UserVoterRelationTest.php` (`'creating user with required data and campaign auto-creates voter record'`, `'comando users:create-voter-records creates voters for existing users'`) start failing after adding the exclusion rule.

### Pitfall 2: Global unique constraint removal race condition
**What goes wrong:** If `duplicate_sequence` assignment (`max(duplicate_sequence) + 1`) is computed and then saved in two non-atomic steps, concurrent registrations of the same cédula by two leaders at the same moment could both compute the same next sequence number and collide on the composite unique index, causing an unhandled `QueryException` instead of a graceful duplicate flow.
**Why it happens:** Read-then-write without a DB-level lock or retry.
**How to avoid:** Wrap the sequence computation + insert in a `DB::transaction()` with `lockForUpdate()` on the matching `document_number` rows, or catch the unique-constraint `QueryException` and retry once with the next sequence value.
**Warning signs:** Flaky duplicate-creation tests, or production errors mentioning the composite unique index name under concurrent registration load (e.g., Día D bulk registration bursts).

### Pitfall 3: `deleted_at` (soft deletes) interaction with the composite unique index
**What goes wrong:** `Voter` uses `SoftDeletes`. The existing form-level rule already special-cases this with `Rule::unique(...)->whereNull('deleted_at')` plus a manual `withTrashed()` check. A naive DB-level composite unique on `(document_number, duplicate_sequence)` does **not** know about `deleted_at` — a soft-deleted record still occupies its `(document_number, duplicate_sequence)` slot at the DB level (SQLite/MySQL do not support partial/filtered unique indexes without extra syntax), which could block re-registration after a legitimate soft delete, or double-count sequence numbers when computing `max()+1`.
**How to avoid:** Either (a) compute `max(duplicate_sequence)` including soft-deleted rows via `withTrashed()` so numbering stays monotonic and never collides even after deletes, or (b) exclude soft-deleted rows from the sequence computation but accept that a restored record could theoretically re-collide (unlikely in practice given restore is rare). Recommend (a) — monotonic sequence including trashed rows — for simplicity and to match the existing form validation's `withTrashed()` awareness.
**Warning signs:** `tests/Feature/VoterTest.php`'s existing soft-delete/restore tests (`'can soft delete a voter'`, `'can restore a soft deleted voter'`) combined with any new duplicate-sequence test.

### Pitfall 4: Filament Importer requires new infrastructure tables that don't exist yet
**What goes wrong:** Assuming `ImportAction` "just works" because `filament/filament` is already installed — the `imports`, `failed_import_rows`, `job_batches`, and `notifications` tables do not exist in this project's migrations yet. Without them, the import modal will throw a table-not-found error at runtime.
**How to avoid:** Add an explicit Wave 0 task to publish and run these four migrations before implementing `ApoyoImporter`.
**Warning signs:** `SQLSTATE[HY000]: no such table: imports` (or `job_batches`/`notifications`) the first time `ImportAction` is triggered.

## Open Questions

1. **Does the leader/coordinator exclusion also apply to `admin_campaign` document numbers?**
   - What we know: `UserObserver` auto-creates system voters for any role with `document_number` + `municipality_id` + campaign, not leader/coordinator-specific.
   - What's unclear: The phase name says "exclusión lider-apoyo" (leader-specific); CONTEXT.md's code_context note says "reutilizar tal cual para la validación cruzada líder-apoyo" without mentioning admin_campaign.
   - Recommendation: Scope the rule to `leader` + `coordinator` roles only, matching the literal phase name; flag for user confirmation only if the plan-check step raises it.

2. **Is Gremio/Subcategoria a global catalog or per-campaign?**
   - What we know: `Department`/`Municipality` (the closest existing analog) are global (no `campaign_id`). `Neighborhood` however DOES have a `campaign_id` (nullable, `is_global` flag) per `NeighborhoodsImport`.
   - What's unclear: The client's examples ("Manipulador de Alimentos", "Mototaxista") sound like universal occupational categories, not campaign-specific, but this wasn't explicitly locked in CONTEXT.md decisions.
   - Recommendation: Default to global (no `campaign_id`), matching `Department`/`Municipality`, since D-04 only says "administrable desde Filament" with no mention of campaign scoping. Simpler and reversible (a `campaign_id` column could be added later without breaking anything).

3. **Exact UX mechanics of "reassignment of owner" (D-03) — does it move `registered_by`, `campaign_id`, both, or swap which duplicate row is the canonical `-0`?**
   - What we know: The client wants an admin to be able to resolve "internal debate" over which leader legitimately owns a disputed cédula, with mandatory note + auto who/when audit.
   - What's unclear: Whether resolution changes the `duplicate_sequence`/status of the *existing* rows (e.g., promote row `-1` to become the new canonical owner, demoting the old `-0`) or simply changes `registered_by` on one row while leaving sequence numbers as an immutable historical record.
   - Recommendation: Treat `duplicate_sequence` as an immutable registration-order marker (never renumbered) and let "reassignment" mean: pick one duplicate row, set its `status` back to its pre-dispute normal status (e.g., `PENDING_REVIEW` or the status it would have had), optionally soft-delete or explicitly mark the losing duplicate rows, and write the `validation_histories` entry. This preserves full audit history and avoids ever mutating the `-N` numbers users have already seen. Flag this interpretation to the user during planning if the plan-check step surfaces ambiguity.
