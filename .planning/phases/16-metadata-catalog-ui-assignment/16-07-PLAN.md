Then, inside the existing `->action(function (array $data, User $record): void { ... })` closure, add a hard write-time gate as the FIRST line of the closure body, mirroring `MetadataAssignmentPanel::assign()` exactly:

```php
abort_unless(
    app(MetadataAssignmentService::class)->canAssignTo(auth()->user(), $record),
    403,
);
```

Everything else inside that closure (the `assign()` call and the success `Notification`) stays unchanged.

In `bulkAction()`, replace the entire `->action(function (Collection $records, array $data): void { ... })` closure body with a version that re-filters `$records` through `subordinatesByIds()` before writing anything, mirroring `leaders.blade.php`'s `assignBulkMetadata()`:

```php
->action(function (Collection $records, array $data): void {
    $service = app(MetadataAssignmentService::class);
    $actor = auth()->user();

    $targets = $service->subordinatesByIds($actor, $records->pluck('id')->all());

    if ($targets->isEmpty()) {
        Notification::make()
            ->title('No tienes autorización para asignar metadata a los usuarios seleccionados.')
            ->danger()
            ->send();

        return;
    }

    $assigned = $service->assignMany(
        subjects: $targets,
        key: MetadataKey::findOrFail($data['metadata_key_id']),
        value: (string) $data['value'],
        assignedBy: $actor,
    );

    Notification::make()
        ->title("Metadata asignada a {$assigned} usuario(s)")
        ->success()
        ->send();
})
```

This single edit fixes both the authorization gap AND the info-level anti-pattern noted in `16-VERIFICATION.md` (a success notification firing on a 0-record no-op) — a `$targets->isEmpty()` write never reaches the success branch anymore.

Do not touch `modalSchema()`, `typeOf()`, or `optionsOf()` — those are unaffected by this gap.

No new imports are needed: `User`, `MetadataKey`, `MetadataAssignmentService`, `Notification`, and `Collection` are all already imported in this file.
