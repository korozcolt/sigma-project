## registraduria-interactive-result-not-parsed — Interactive Registraduria lookup showed generic error and, once fixed, crashed on save due to blank DIVIPOLE codes
- **Date:** 2026-07-26
- **Error patterns:** Error desconocido al consultar la Registraduria, QueryException, Incorrect integer value, zone_code, puesto_codigo, zona_codigo, raw_message_html, polling_places, NOT NULL
- **Root cause:** (1) RegistraduriaController::result() returned the Python microservice's raw JSON passthrough (unparsed raw_message_html) to the Alpine.js polling loop, instead of the parsed fields that RegistraduriaService::getResult() produces via parseConsultaHtml() — so a real success looked like a generic error because puesto_nombre was missing. (2) Real Registraduria HTML responses never include a "CODIGO PUESTO"/"ZONA" column, so puesto_codigo/zona_codigo are always empty string (not an edge case — the normal case). HasRegistraduriaPolling::fillPollingPlaceFields() and PollingPlaceResolver::resolveOrCreatePollingPlace() both used `?? null`/`?? substr(...)` fallbacks that never triggered (since the keys always existed, just blank), so '' was inserted into NOT NULL unsignedSmallInteger zone_code/place_code columns, crashing with QueryException 1366.
- **Fix:** Extracted parsing into a shared static `RegistraduriaService::normalizeResultPayload()` called by both the controller and the service. Made `polling_places.zone_code`/`place_code` nullable via migration. Made `PollingPlaceResolver::resolveOrCreatePollingPlace()` public and rewrote it to use `filled()` checks (blank string -> null) with name-based match/create when codes are blank (following the existing `resolveFromCampaignCensus()` precedent). `HasRegistraduriaPolling::fillPollingPlaceFields()` now delegates to the resolver instead of duplicating the logic.
- **Files changed:** app/Services/RegistraduriaService.php, app/Http/Controllers/RegistraduriaController.php, app/Services/PollingPlaceResolver.php, app/Filament/Resources/Voters/Concerns/HasRegistraduriaPolling.php, database/migrations/2026_07_26_164628_make_zone_and_place_code_nullable_in_polling_places.php, tests/Feature/RegistraduriaControllerTest.php, tests/Feature/Services/PollingPlaceResolverTest.php, tests/Feature/Filament/VoterRegistraduriaRefreshTest.php

## status-polling-place-source-desync — Estado badge contradicts polling-place-source badge (Pendiente de Revision next to En Vivo)
- **Date:** 2026-08-05
- **Error patterns:** Pendiente de Revision, En Vivo, status, polling_place_source, badge, contradictorio, estado, fuente del puesto de votacion, PENDING_REVIEW, LIVE, desincronizado, apoyos table, VotersTable
- **Root cause:** Voter.status and Voter.polling_place_source are two independent state machines on the same model, updated by two separate uncoordinated hourly cron jobs (routes/console.php: census:reconcile-live -> ReconcileFallbackPollingPlaces only wrote polling_place_source; census:reconcile-validation -> DispatchCensusRevalidation/VoterValidationService only wrote status), so a voter could sit with a stale non-terminal status while polling_place_source was already LIVE for hours/days under backlog. A second, inverse desync existed in register-voter.blade.php's manual creation flow: status = VERIFIED_REGISTRADURIA was set without also setting polling_place_source. NOTE: an earlier, wrongly-framed debug session (estado-badge-visual-misalign-voters-table) investigated this as a CSS/rendering "badges stacked in one cell" bug and came back inconclusive — it was actually a data/logic desync between the two badges' VALUES, not a rendering defect.
- **Fix:** ReconcileFallbackPollingPlaces::handle() now injects VoterValidationService and calls updateVoterStatus($voter, found: true) inside the existing `$result->source === PollingPlaceSource::LIVE` branch, reusing the already-fetched LIVE result (zero new resolver/live-adapter calls). register-voter.blade.php's Voter::create() now also sets polling_place_source/polling_place_resolved_at whenever $foundInRegistraduria is true. Added a new resolver-free `census:backfill-live-status-desync` Artisan command (App\Console\Commands\BackfillLiveStatusDesync) to remediate already-affected historical voters, operating purely on already-persisted data (--dry-run supported); a dedicated test asserts the resolver/live adapters are never invoked. A production `--dry-run` on sigma-betha then surfaced that `VoterValidationService::NON_DOWNGRADABLE_STATUSES` was missing `VoterStatus::DUPLICATE`/`CORRECTION_REQUIRED` (both manual-intervention states) — added both to the guard before running the real write, to avoid silently reclassifying disputed/duplicate voters.
- **Files changed:** app/Jobs/ReconcileFallbackPollingPlaces.php, resources/views/livewire/leader/register-voter.blade.php, app/Console/Commands/BackfillLiveStatusDesync.php, app/Services/VoterValidationService.php, tests/Feature/Jobs/ReconcileFallbackPollingPlacesTest.php, tests/Feature/Leader/RegisterVoterRegistraduriaLookupTest.php, tests/Feature/Console/BackfillLiveStatusDesyncTest.php, tests/Feature/RevalidationCoverageTest.php, tests/Feature/VoterValidationServiceTest.php, tests/Feature/CensusUnifiedResolutionTest.php, tests/Feature/VoterCensusValidationTest.php
- **Production execution (2026-08-05):** Deployed commits de5f20e + 87f9351 to both Laravel apps (autoDeploy, ~10min queued). Aldemar: 0 apoyos affected (dry-run clean). sigma-betha: 1099 apoyos had polling_place_source=LIVE — 1095 already correctly VERIFIED_CENSUS (the sibling validation job had already caught up naturally by the time the backfill ran; command re-confirmed them, adding 1095 ValidationHistory audit rows but 0 status changes) and 4 were DUPLICATE, correctly skipped by the new guard. 0 voters were found in the contradictory PENDING_REVIEW+LIVE state at execution time — the visible backlog from the original screenshot had already self-cleared; the code fix prevents recurrence. Zero paid Registraduria/2captcha lookups triggered throughout.

## polling-place-id-not-persisted-by-resolver — "N apoyos válidos sin puesto de votación asignado" widget count inflated, ranking undercounted
- **Date:** 2026-08-05
- **Error patterns:** sin puesto de votacion asignado, Ranking de Puestos de Votacion, TopPollingPlacesTable, polling_place_id, polling_place_source, apoyos validos, NULL FK
- **Root cause:** `PollingPlaceResolver::persist()` (app/Services/PollingPlaceResolver.php) only wrote `polling_place_source`/`polling_place_resolved_at` to the Voter — never `polling_place_id`, even though every `resolve*()` method already computed it via `resolveOrCreatePollingPlace()`. This is the sole write path for the entire automated cascade (`resolveAutomated()`, used by `ReconcileFallbackPollingPlaces` and `VoterValidationService`), so `polling_place_source` could be correctly resolved while `polling_place_id` stayed NULL forever — inflating the widget's "sin puesto asignado" count and undercounting the ranking table (which counts via the `PollingPlace::voters()` relation, i.e. depends on `polling_place_id`). Confirmed with real data: 507-526 of ~529 affected sigma-betha voters already had `polling_place_source=LIVE`.
- **Fix:** `persist()` now writes `polling_place_id` whenever the result carries one, without ever nulling out an existing good FK on an incomplete re-resolution. New resolver-free `census:backfill-polling-place-id` Artisan command re-derives `polling_place_id` for historical voters using only local reads matching their existing `polling_place_source` (LIVE→`resolveFromPermanentLookup`, SNAPSHOT→`resolveFromNationalSnapshot`, DB_RECONSTRUCTION→`resolveFromCampaignCensus`), never touching a live/2captcha adapter.
- **Production execution:** Aldemar 0 affected. sigma-betha: 526 candidates, 512 linked, 14 skipped (municipio name didn't match `municipalities` table — safe, expected).
- **Files changed:** app/Services/PollingPlaceResolver.php, app/Console/Commands/BackfillPollingPlaceId.php, tests/Feature/Services/PollingPlaceResolverTest.php, tests/Feature/Console/BackfillPollingPlaceIdTest.php

## top-polling-places-rank-resets-per-page — Ranking "#" trophy/star badge resets to #1/#2/#3 on every page instead of showing true overall rank
- **Date:** 2026-08-05
- **Error patterns:** Ranking de Puestos de Votacion, TopPollingPlacesTable, rowLoop, iteration, trophy, badge, rank resets, pagination, PaginationMode Simple, Siguiente, apoyos_count, TableWidget
- **Root cause:** The `ranking` column's `->state()`/`->color()`/`->icon()` closures in `TopPollingPlacesTable::table()` all keyed on `$rowLoop->iteration` (Blade/Livewire's per-page loop index), which always restarts at 1 at the top of every page since `Filament\Widgets\TableWidget` forces `PaginationMode::Simple`. This made every page's top 3 rows incorrectly show the #1 trophy / #2-#3 star treatment, instead of only the true overall #1/#2/#3 by `apoyos_count` descending.
- **Fix:** Added `public static TopPollingPlacesTable::resolveAbsolutePosition(mixed $livewire, ?stdClass $rowLoop): int` that computes `(($livewire->getTablePage() - 1) * $livewire->getTableRecordsPerPage()) + $rowLoop->iteration`, with a defensive fallback to `$rowLoop->iteration` if per-page isn't numeric (e.g. `'all'`). Both `$livewire` and `$rowLoop` are available as named closure parameters via Filament's `Column::resolveDefaultClosureDependencyForEvaluationByName()`; `getTablePage()`/`getTableRecordsPerPage()` come from `Filament\Tables\Concerns\CanPaginateRecords` (used by every `InteractsWithTable` Livewire component, including all `TableWidget`s). Left `PaginationMode::Simple` and the base query's `->limit(10)` untouched — confirmed inert once paginated, since `simplePaginate()`'s internal `->take($perPage)` always overrides any prior `->limit()`. Also discovered and documented (not fixed, since it's inherent to Filament, not a bug): `assertTableColumnStateSet()` in tests reads the column's cached `$rowLoop`, which is mutated to the LAST rendered row of the page — so it can't correctly assert row-position-dependent state for an arbitrary record; work around by asserting against the page's actual last row, and/or calling the now-public resolver method directly with a hand-built loop object.
- **Files changed:** app/Filament/Widgets/TopPollingPlacesTable.php, tests/Feature/Filament/TopPollingPlacesTableTest.php

## document-number-digits-exact-10-too-strict — cédulas de menos de 10 dígitos rechazadas al crear líder/apoyo
- **Date:** 2026-08-05
- **Error patterns:** debe tener 10 dígitos, document number, digits:10, document_number, Agregar Apoyo, Registrar Apoyo, cédula, NUIP
- **Root cause:** 3 formularios independientes (coordinator/leader-add-voter.blade.php, leader/register-voter.blade.php, PublicVoterRegistrationController) usaban `digits:10` (exacto) para `document_number`, pero las cédulas/NUIP colombianas van de 6 a 11 dígitos. Además faltaba `document_number` en `lang/es/validation.php`'s attributes, mostrando el nombre crudo en inglés.
- **Fix:** `digits:10` → `digits_between:6,11` en los 3 sitios (más sus gates `preg_match` que disparan el autofill de identidad/Registraduría). Agregada traducción `document_number => 'Número de Documento'`.
- **Files changed:** lang/es/validation.php, resources/views/livewire/coordinator/leader-add-voter.blade.php, resources/views/livewire/leader/register-voter.blade.php, app/Http/Controllers/PublicVoterRegistrationController.php

## voter-territory-scope-ignores-resolved-polling-place — apoyos fuera de municipio no se rechazaban si polling_place difería de voter.municipality_id
- **Date:** 2026-08-05/06
- **Error patterns:** alcance territorial, jurisdicción, Dentro/Fuera, REJECTED_OUT_OF_SCOPE, VoterTerritoryScope, municipality_id, polling_place_id, Ranking de Puestos de Votación municipio distinto
- **Root cause:** La nueva validación de alcance territorial (y los 3 widgets de jurisdicción de los que se extrajo) comparaban el municipio de la campaña contra `voter.municipality_id` — un campo autocompletado con el municipio de la campaña al crear el apoyo y NUNCA actualizado cuando el puesto de votación real se resuelve después en otro municipio. 16 apoyos reales en sigma-betha tenían su puesto de votación resuelto en Morroa/Palmito/Sampués/etc. pero `municipality_id` seguía diciendo Sincelejo.
- **Fix:** `VoterTerritoryScope::isWithinCampaignScope()` ahora usa el municipio/departamento del `polling_place` resuelto (fuente de verdad de Registraduría/censo) cuando existe, cayendo a `voter.municipality_id` solo si no hay puesto resuelto.
- **Production execution:** 18 apoyos correctamente marcados REJECTED_OUT_OF_SCOPE en sigma-betha tras el fix (16 discrepancias identificadas + 2 adicionales).
- **Files changed:** app/Services/VoterTerritoryScope.php, tests/Feature/Services/VoterTerritoryScopeTest.php

## voter-status-match-missing-cases — 500 al ver/listar apoyos con status nuevo o ya existente (match no exhaustivo)
- **Date:** 2026-08-06
- **Error patterns:** Unhandled match case, App\Enums\VoterStatus, ViewVoter, nextStepGuidance, VotersTable, 500 error del servidor
- **Root cause:** `ViewVoter::nextStepGuidance()` y el `->color()` de la columna status en `VotersTable` son `match($voter->status)` SIN `default`. El primero ya le faltaban CENSUS_NOT_FOUND y VERIFIED_REGISTRADURIA desde antes (sin tests que lo cubrieran); ambos les faltaba el REJECTED_OUT_OF_SCOPE recién agregado, causando 500 real en producción al ver o listar cualquier apoyo con ese estado.
- **Fix:** Agregados los casos faltantes en ambos matches. Nuevos tests parametrizados (`->with(VoterStatus::cases())`) que renderizan ViewVoter y ListVoters para los 12 estados — cualquier caso nuevo del enum que se olvide en un match no exhaustivo ahora falla en CI, no en producción.
- **Files changed:** app/Filament/Resources/Voters/Pages/ViewVoter.php, app/Filament/Resources/Voters/Tables/VotersTable.php, tests/Feature/Filament/VoterResourceTest.php

## report-widgets-scope-count-failures — 17 Pest test failures across Filament report/stat widgets tied to campaign scope and counts
- **Date:** 2026-08-12
- **Error patterns:** Failed asserting that true is false, Failed asserting that 0 is identical to, canView, assertSee, JurisdictionReportTable, JurisdictionSummaryOverview, RejectionsCountersOverview, TopCoordinatorsTable, TopPollingPlacesTable, DuplicatesReportTable, VoterResourceTest, department_id, CampaignContext, campaign_context, whereRaw 1 = 0, serial test run
- **Root cause:** App\Services\CampaignContext caches the active-campaign selection in `private static` properties (`$overrideCampaignId`, `$overrideMode`), mutated by `CampaignContext::setCampaignId()`. These statics are process-scoped, so in a serial `php artisan test` run every Feature/E2E test file shares one PHP process and the statics leak across unrelated files. `setCampaignId(null)` (used as "cleanup" in several older test files) doesn't truly unset the override — it pins `$overrideMode` to `'all'`, and `sessionCampaignId()` checks `$overrideMode === 'all'` before ever reading `Session::get('campaign_context.campaign_id')`. So any later test that sets context the production way via `Session::put('campaign_context.mode'|'campaign_id', ...)` gets silently ignored, `currentCampaign()` resolves null, and `canView()`/stat widgets/table widgets all hit their no-active-campaign fallback branches. This was a previously-known, previously-worked-around-per-file issue (3 older test files already had a commented ReflectionClass-based afterEach reset) that 8 newer report-widget/voter test files (added 2026-07-30/08-05) never adopted.
- **Fix:** Overrode `tests/TestCase.php::tearDown()` to reset `CampaignContext::$overrideCampaignId`/`$overrideMode` back to `null` via `ReflectionClass` after every single test, before `parent::tearDown()`. (Note: a global Pest `afterEach(...)->in('Feature')` hook in tests/Pest.php was tried first but never fired — `.in()` chaining on bare before/afterEach calls doesn't reliably scope hooks in this Pest version; `tearDown()` override is the reliable fix.) Test-suite-only change; no production code touched.
- **Files changed:** tests/TestCase.php

## apoyo-marcado-en-vivo-con-puesto-sin-resolver — apoyo con polling_place_source=live y polling_place_id NULL, "Sin resolver" en ViewVoter pese al badge En Vivo
- **Date:** 2026-08-30
- **Error patterns:** En Vivo, Sin resolver, polling_place_source, polling_place_id NULL, resolveOrCreatePollingPlace, whereRaw LOWER(name), municipio, TOLUVIEJO, BOGOTA D.C., COLOSO RICAURTE, tilde, acento, paréntesis, ReconcileFallbackPollingPlaces, verified_census, found true hardcoded
- **Root cause:** Two independent bugs. (1) `PollingPlaceResolver::resolveOrCreatePollingPlace()` matched `Municipality` with an EXACT `whereRaw('LOWER(name) = ?', ...)` — real live Registraduría `municipio` strings carry formatting variance the seeded catalog (from api-colombia.com via `ImportColombiaData`) never has: missing accents+word-spacing ("TOLUVIEJO" vs "Tolú Viejo"), missing accent+extra punctuation ("BOGOTA. D.C." vs "Bogotá D.C."), and parenthetical alternate/historical names ("COLOSO (RICAURTE)" vs "Coloso") — all 4 real affected local-backup voters (ids 88, 89, 116, 153) were genuine catalog entries, not missing municipalities. (2) `PollingPlaceResolver::persist()` wrote `polling_place_source='live'`/`polling_place_resolved_at` UNCONDITIONALLY regardless of whether `pollingPlaceId` resolved, which also silently removed the voter from `ReconcileFallbackPollingPlaces`'s candidate query (excludes `source=live`), stranding it with no automatic retry forever — this is why every affected voter also had `status=verified_census` (the resolver's LIVE-tagged-but-incomplete result flowed straight into `updateVoterStatus(found: true)`).
- **Fix:** New `Municipality::findByFuzzyName()`/`normalizeName()` (`Str::ascii` + strip parenthetical suffixes + strip punctuation/whitespace + uppercase; tries exact match first; returns null — never guesses — when normalization matches more than one catalog entry, e.g. cross-department homonyms like "Granada" ×3, a PRE-EXISTING ambiguity the old exact-match path was already blind to). Used in both `PollingPlaceResolver::resolveOrCreatePollingPlace()` and the interactive flow's duplicate matcher in `HasRegistraduriaPolling::fillPollingPlaceFields()`. `persist()` now refuses to write `source=LIVE` when `pollingPlaceId` is null. This required decoupling `resolveAutomated()`'s return value ("genuine census/Registraduría find," read by `VoterValidationService::validateAgainstCensus()`) from "polling place actually persisted" (now checked via the voter's own persisted `polling_place_source` in `ReconcileFallbackPollingPlaces` and via `persist()`'s return value in `CollectRegistraduriaLookupResult`) — otherwise the guard silently broke "found in census" detection for cases where a genuine census match exists but the municipality can't be resolved. New `census:backfill-live-unresolved --dry-run` command reverts affected voters (`polling_place_source=live AND polling_place_id IS NULL`) to unresolved so the existing hourly `census:reconcile-live` re-derives them for free via the already-cached `registraduria_lookups` row (verified end-to-end against sigma_betha_backup: all 4 known-affected voters resolved correctly with a real `polling_place_id`, zero 2captcha spend). The dry-run also reports per-voter whether the new fuzzy matcher would resolve their cached `municipio` string, so an operator can audit the full list of real production mismatches before deciding if any residual case needs a catalog fix instead. Two pre-existing tests (`tests/Feature/VoterValidationServiceTest.php`, `tests/Feature/RevalidationCoverageTest.php`) had inadvertently codified this exact bug as their own assertions (`polling_place_source` expected to become LIVE even with an unmatched random Faker municipio) — corrected to test the intended "found in census" vs "polling place resolved" distinction.
- **Files changed:** app/Models/Municipality.php, app/Services/PollingPlaceResolver.php, app/Filament/Resources/Voters/Concerns/HasRegistraduriaPolling.php, app/Jobs/ReconcileFallbackPollingPlaces.php, app/Jobs/CollectRegistraduriaLookupResult.php, app/Console/Commands/BackfillLiveUnresolved.php, tests/Unit/Models/MunicipalityFuzzyMatchTest.php, tests/Feature/Services/PollingPlaceResolverTest.php, tests/Feature/Jobs/ReconcileFallbackPollingPlacesTest.php, tests/Feature/Jobs/CollectRegistraduriaLookupResultTest.php, tests/Feature/Console/BackfillLiveUnresolvedTest.php, tests/Feature/VoterValidationServiceTest.php, tests/Feature/RevalidationCoverageTest.php
