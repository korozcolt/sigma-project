<objective>
Close REPT-03 — the single biggest gap found in the Phase 05.1 audit. `CoordinatorPanelProvider`/`LeaderPanelProvider` already register real, working widgets (`CampaignStatsOverview`, `TerritorialDistributionChart`, `ValidationProgressChart`, `TopLeadersTable`) — but every one of them scopes by campaign ONLY, identical to what an admin sees. A coordinator's `TopLeadersTable` currently ranks ALL leaders in the campaign, not just their own team.

Purpose: give coordinators and leaders dashboards scoped to their own ownership/territory, mirroring the `Auth::id()`-scoping pattern `CallCenterStatsOverview` already proves out for reviewers — per this phase's explicit discretion note to prefer explicit `Auth::id()`/`hasRole()` branching over any implicit global scope, given the related CAMP-05 finding that global scopes silently no-op outside an authenticated request context.
Output: 4 existing widget classes gain role-based ownership branches; admin behavior is unchanged.
</objective>

<interfaces>
Existing precedent to mirror exactly — `app/Filament/Widgets/CallCenterStatsOverview.php`:
```php
$stats = $callCenterService->getReviewerStats(Auth::id());
```
No campaign-context indirection, no global scope reliance — straight `Auth::id()` into a service/query method. Do not build a generic polymorphic "scope resolver" — only 4 widgets need this, and per this phase's research, explicit branches per widget (matching the codebase's existing style) are preferred over an abstraction.

Ownership relations already exist on `User` (no model changes needed):
```php
public function coordinator(): BelongsTo { return $this->belongsTo(User::class, 'coordinator_user_id'); }
public function leaders(): HasMany { return $this->hasMany(User::class, 'coordinator_user_id'); }
```
So: a **leader's own scope** = `Voter::where('registered_by', Auth::id())`. A **coordinator's team scope** = `Voter::whereIn('registered_by', Auth::user()->leaders()->pluck('id'))`.

Panel widget registrations (confirmed, no changes needed in this plan — only the widget classes' internal query logic changes):
- `AdminPanelProvider`: `CampaignStatsOverview, ValidationProgressChart, TerritorialDistributionChart, TopLeadersTable, TopCoordinatorsTable, ...` (admin sees unrestricted data — `Auth::user()` for an admin has no `coordinator`/`leader` role, so the new branches below never trigger for them)
- `CoordinatorPanelProvider`: `CampaignStatsOverview, TerritorialDistributionChart, TopLeadersTable`
- `LeaderPanelProvider`: `CampaignStatsOverview, ValidationProgressChart, TerritorialDistributionChart` (does NOT register `TopLeadersTable` — a leader ranking other leaders makes no sense, so `TopLeadersTable` needs no leader-role branch)

`App\Enums\UserRole` values used below: `UserRole::COORDINATOR->value` = `'coordinator'`, `UserRole::LEADER->value` = `'leader'`.

    {

        return $table
            ->query(
                fn (): Builder => User::query()
                    ->when($activeCampaign, function ($query) use ($activeCampaign) {

                    })

                        fn ($query) => $query->where('coordinator_user_id', $user->id)

                    ->limit(10)
            )
            // ... rest of the method (columns, headerActions, paginated(false)) unchanged

    use App\Models\Campaign;
    use Illuminate\Support\Facades\Auth;
    use Illuminate\Database\Eloquent\Builder;
    // ...
    private function scopedVoterQuery(Campaign $campaign): Builder
    {
        $user = Auth::user();
        $query = Voter::where('campaign_id', $campaign->id);

        if ($user?->hasRole(UserRole::LEADER->value)) {

        }

        return $query;
    }
