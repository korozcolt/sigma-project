**Filament "Modo Mantenimiento" page toggles Laravel's native maintenance mode with a Super Admin bypass via the documented `--secret` link, auto-applied to the activating admin's own session**

## Accomplishments

- A Super Admin can take the whole app offline for maintenance from the UI (Configuración > Modo Mantenimiento), with zero server/CLI access needed
- Every other role (admin_campaign, coordinator, leader) sees Laravel's standard 503 maintenance page while it's active
- The Super Admin who activates maintenance mode automatically bypasses it for their own session immediately, via the native `--secret` bypass mechanism, and can hand the same link to other Super Admins on other devices/sessions
- Live two-session browser verification (Super Admin + non-super-admin) confirmed the full flow end-to-end, including the fix described below

## Decisions Made

- Abandoned the plan's primary `MaintenanceModeException` render-null approach after confirming that exception class doesn't exist in this Laravel version, and that `PreventRequestsDuringMaintenance` throws before session/auth middleware runs regardless — used the plan's own pre-authorized `--secret` fallback instead (`bootstrap/app.php` untouched)
- Kept the bypass-link notification for other Super Admin sessions/devices, and added an immediate in-session redirect for the activating admin specifically (checkpoint-discovered requirement, not in the original plan text)

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Activating admin's own session got 503'd immediately after turning maintenance mode ON**
- **Found during:** Task 3 (checkpoint:human-verify) — user's first live-browser test attempt: clicked "Activar Mantenimiento" as Super Admin and immediately got a 503 page themselves (confirmed by screenshot)
- **Issue:** Laravel's maintenance bypass cookie is only set when the `/{secret}` URL is actually visited. Task 2's implementation generated the secret and displayed it in a Filament notification, but never applied the bypass to the activating admin's own current session — so their very next request (e.g. any navigation after the action) hit `PreventRequestsDuringMaintenance` and got 503'd too, exactly like every other non-bypassed role
- **Fix:** After `Artisan::call('down', [...])`, the action now calls `$this->redirect(url('/'.$secret))` to immediately navigate the activating admin's own browser through the secret URL, so their session gets the bypass cookie right away. The notification still shows the link too, for other Super Admins on other sessions/devices
- **Files modified:** `app/Filament/Pages/MaintenanceKillSwitch.php`, `tests/Feature/MaintenanceKillSwitchTest.php`
- **Verification:** New test `'activating maintenance mode immediately redirects the acting super admin through the bypass secret, not just showing it in a notification'` (`Livewire::actingAs($superAdmin)->test(MaintenanceKillSwitch::class)->callAction('toggleMaintenance')->assertRedirect()`) passes; user re-tested live in browser afterward and confirmed correct behavior (activation no longer locks out the activating admin, other-role 503 behavior confirmed separately, deactivation restores normal operation for all sessions)
- **Committed in:** `3f78e7d` on `main` (applied directly by the orchestrating session during the checkpoint pause), cherry-picked into this plan's branch as `bc815e6` to keep this worktree's history consistent with what was verified
