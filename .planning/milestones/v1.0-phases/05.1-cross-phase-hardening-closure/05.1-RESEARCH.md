## Architecture Patterns

### 1. PERM-02 — Reason-specific denial messages

**Root cause (broader than CONTEXT.md's two call sites):** There are actually **three** independent places generic denials originate:
1. `EnsureUserHasRole.php:32` — `abort(403, 'No tienes permiso para acceder a esta sección')` (route middleware, panel access)
2. `CampaignContext.php:125` / `:147` — generic `RuntimeException` (write-time campaign enforcement)
3. `AuthServiceProvider.php` `Gate::before()` — returns bare `false` for cross-campaign model denial (Filament policy checks), which Laravel renders as the fully generic **"This action is unauthorized."**

**Pattern: `Illuminate\Auth\Access\Response::deny($message)` instead of returning `false`/`true`/`null` from `Gate::before`.**

```php
// app/Providers/AuthServiceProvider.php — boot()
use Illuminate\Auth\Access\Response;

Gate::before(function ($user, string $ability, array $arguments = []) {
    if (CampaignContext::isSuperAdmin($user)) {
        return null; // defer to normal policy checks
    }

    $campaignId = CampaignContext::currentCampaignId($user);
    if (! $campaignId) {
        return null;
    }

    $model = $arguments[0] ?? null;

    if ($model instanceof User) {
        return $model->campaigns()->whereKey($campaignId)->exists()
            ? null
            : Response::deny('Este usuario no pertenece a la campaña activa.');
    }

    if ($model instanceof Model && $model->getAttribute('campaign_id')) {
        return (int) $model->getAttribute('campaign_id') === (int) $campaignId
            ? null
            : Response::deny('Este registro pertenece a otra campaña y no es accesible desde tu contexto actual.');
    }

    return null;
});
```

When `Gate::authorize()`/policy-driven Filament actions fail, Laravel's `AuthorizationException` carries the `Response::deny()` message through automatically — `$exception->getMessage()` returns the custom string, and Filament's own exception handling surfaces it in the 403 page/notification. **Confidence: HIGH** (verified against Laravel 12 docs — `Response::deny()` propagates its message to the thrown `AuthorizationException`).

For role-boundary denials (source #1) and campaign-context write denials (source #2), the cleanest approach given this codebase's structure is a small **custom exception class** (`app/Exceptions/OperationalDenialException.php` extends `RuntimeException`) that both `EnsureUserHasRole` and `CampaignContext` throw with a reason enum/string, paired with a `withExceptions()` render closure in `bootstrap/app.php`:

```php
// bootstrap/app.php
->withExceptions(function (Exceptions $exceptions): void {
    $exceptions->render(function (AuthorizationException $e, Request $request) {
        if ($request->expectsJson()) {
            return response()->json(['message' => $e->getMessage()], 403);
        }
        // Let Filament/Livewire's normal notification flow show $e->getMessage()
    });

    $exceptions->render(function (OperationalDenialException $e, Request $request) {
        // Same treatment — surfaces $e->getMessage() instead of a generic string
    });
})
```

**Don't build:** a whole new "permission reason" framework/package. The three denial sources are few enough to fix directly at their source with `Response::deny()` (for Gate) and a shared exception class (for middleware/service-level denials) — no abstraction layer needed.

### 2. Kill switch — native maintenance mode + Filament action + super-admin bypass

Laravel's native maintenance mode (`php artisan down`/`up`) already persists a `storage/framework/down` flag file read by `Illuminate\Foundation\Http\Middleware\PreventRequestsDuringMaintenance` — no custom flag storage needed. Two integration points:

**A. Trigger from a Filament action (not a console command):**
```php
use Illuminate\Foundation\Console\DownCommand;
use Illuminate\Support\Facades\Artisan;

Action::make('toggleMaintenance')
    ->label(fn () => app()->isDownForMaintenance() ? 'Desactivar Mantenimiento' : 'Activar Mantenimiento')
    ->requiresConfirmation()
    ->action(function () {
        if (app()->isDownForMaintenance()) {
            Artisan::call('up');
        } else {
            Artisan::call('down', [
                '--secret' => Str::random(40), // optional bypass link
                '--retry' => 60,
            ]);
        }
    })
    ->visible(fn () => Auth::user()?->hasRole(UserRole::SUPER_ADMIN->value) ?? false);
```
`Artisan::call('down')`/`Artisan::call('up')` work fine from within a web request (no need to shell out) — Laravel's console commands are just classes; calling them programmatically is the documented approach for exactly this "trigger maintenance mode from the app itself" use case. **Confidence: HIGH** (standard Laravel `Artisan::call()` usage).

**B. Super-admin automatic bypass (no shared secret needed for the role itself):** Laravel 12's `bootstrap/app.php` supports `->withMiddleware(fn (Middleware $middleware) => $middleware->statefulApi())` style config but for maintenance-mode exceptions the actual hook is `PreventRequestsDuringMaintenance::except()`/config, or — cleaner for a role-based bypass — a **custom middleware placed *before* `PreventRequestsDuringMaintenance` in the global stack** that checks `Auth::user()?->hasRole('super_admin')` and lets the request through by calling `$next($request)` without ever reaching the maintenance check. Concretely: register your own `BypassMaintenanceForSuperAdmin` middleware and prioritize it ahead of the framework's maintenance middleware via `$middleware->prependToGroup('web', ...)` or `$middleware->priority([...])` in `bootstrap/app.php`. This avoids depending on cookies/secrets and ties the bypass directly to the authenticated role, matching the "automatic bypass" requirement. **Confidence: MEDIUM** — the secret-URL bypass is officially documented and HIGH confidence; the role-based prepend-priority approach is a standard, well-known Laravel pattern but should be smoke-tested during implementation (verify middleware ordering actually short-circuits `PreventRequestsDuringMaintenance` before session/auth state is even available — auth state requires `StartSession`+`Authenticate` to have already run, so the bypass middleware must run **after** those, meaning it can't be "before" in the literal sense — it must instead be excluded via the `except` mechanism combined with a route check, OR simpler: catch `MaintenanceModeException` in `withExceptions()->render()` and re-check auth there before deciding whether to show the maintenance page).

**Simpler, more robust alternative (recommended):** catch `Illuminate\Foundation\Http\Exceptions\MaintenanceModeException` in `bootstrap/app.php`'s `withExceptions()` and, if the currently authenticated user is `super_admin`, let the request proceed by returning `null`/re-invoking; if not, show the standard 503 view. This sidesteps middleware-ordering fragility entirely and keeps the whole kill switch in one file:

```php
$exceptions->render(function (MaintenanceModeException $e, Request $request) {
    if (Auth::check() && Auth::user()->hasRole('super_admin')) {
        return null; // returning null lets Laravel continue normal (non-maintenance) handling for this request in Laravel 11+/12
    }
    // fall through to default 503 handling
});
```
**Confidence: MEDIUM** — this exact "return null to bypass" pattern for `MaintenanceModeException` should be verified with a quick manual test in Wave 0/1 (the render-closure contract for this specific exception type was not independently confirmed against a live app in this research pass); if it doesn't bypass cleanly, fall back to the documented `--secret` link stored in the super admin's session/bookmark, which is guaranteed to work.

### 3. OTP via Hablame SMS

**Where it wires in:** Codebase inspection shows "leader registration" = the **public, unauthenticated voter self-registration flow** at `PublicVoterRegistrationController::store()` (route `registro/{token}`, gated by `RequireInvitationForRegistration` middleware validating an `Invitation` token). This is a public form with no Laravel auth session — OTP here must be **cache- or DB-backed against the phone number**, not tied to a logged-in user.

**Recommended pattern — DB-backed, not cache-only:** Given this flow is public-facing and campaign-scoped, and given the client wants per-campaign message text, a lightweight `otp_verifications` table (or reusing `Invitation`'s existing `token`/`expires_at` scaffolding) is more auditable than cache alone, and Redis (`predis/predis` is already installed) isn't guaranteed to be the cache driver in every environment. Recommended shape:

```php
// New migration: otp_verifications
Schema::create('otp_verifications', function (Blueprint $table) {
    $table->id();
    $table->string('phone', 10);
    $table->foreignId('campaign_id')->constrained()->cascadeOnDelete();
    $table->string('code', 6);
    $table->timestamp('expires_at');
    $table->unsignedTinyInteger('attempts')->default(0);
    $table->timestamp('verified_at')->nullable();
    $table->timestamps();

    $table->index(['phone', 'campaign_id']);
});
```

**New dedicated service** (follow CLAUDE.md's Actions/Services convention — do not bolt this onto `HablameSmsService`, which is a thin SMS-transport wrapper, not a business-rule owner):

```php
// app/Services/OtpVerificationService.php
class OtpVerificationService
{
    public function __construct(private HablameSmsService $sms) {}

    public function generate(string $phone, Campaign $campaign): OtpVerification
    {
        $code = (string) random_int(100000, 999999);

        $otp = OtpVerification::create([
            'phone' => $phone,
            'campaign_id' => $campaign->id,
            'code' => $code, // hash it, don't store plaintext if the DB isn't encrypted at rest
            'expires_at' => now()->addMinutes(10),
        ]);

        $template = $campaign->settings['otp_message_template']
            ?? 'Tu código de verificación SIGMA es {codigo}. Vence en 10 minutos.';

        $message = str_replace('{codigo}', $code, $template);

        $this->sms->sendRaw($phone, $message, priority: true); // new param, see below

        return $otp;
    }

    public function verify(string $phone, Campaign $campaign, string $code): bool
    {
        $otp = OtpVerification::query()
            ->where('phone', $phone)
            ->where('campaign_id', $campaign->id)
            ->whereNull('verified_at')
            ->latest()
            ->first();

        if (! $otp || $otp->expires_at->isPast() || $otp->attempts >= 5) {
            return false;
        }

        $otp->increment('attempts');

        if (! hash_equals($otp->code, $code)) {
            return false;
        }

        $otp->update(['verified_at' => now()]);
        return true;
    }
}
```

**`Campaign.settings` is already a `json`/`array`-cast column** (`Campaign.php:39,90`) — no migration needed to store `otp_message_template` per campaign, exactly as CONTEXT.md specifies.

**`HablameSmsService` change:** it currently only has `send(Message $message)`, tightly coupled to the `Message` model (with `voter`/`content` relations) — OTP has no `Message`/`Voter` record at the point of sending (registration hasn't happened yet). Add a small `sendRaw(string $phone, string $text, bool $priority = false)` method (or a `priority` param threaded through) that posts directly without requiring a `Message` model, and set `'priority' => true` in the request body per Hablame support's confirmed fix (`.planning/notes/2026-07-23-requisito-nuevo-feature-pendiente.md`) for OTP/transactional sends specifically — do **not** set `priority: true` globally for all SMS (regular messages don't need/shouldn't cost the premium transactional route).

**Wiring into the Livewire/Blade flow:** `PublicVoterRegistrationController::show()`/`store()` is a plain controller, not Volt — add a two-step form (phone entry → OTP entry → rest of form, or a simple "verify phone" AJAX-style sub-step within the existing Blade view) or convert just this sub-flow to a small Volt component embedded in `resources/views/public/voter-registration.blade.php`. **This is a Claude's Discretion item on exact UI treatment** — the load-bearing constraint is that `store()` must reject if no matching `verified_at` OTP exists for that phone+campaign within a short window before creating the `Voter`.

### 4. DB unique constraint on `vote_records(voter_id, election_event_id)` with pre-existing data

**Safe-add pattern (standard, two-phase if needed):**
```php
// database/migrations/2026_xx_xx_add_unique_index_to_vote_records_table.php
public function up(): void
{
    Schema::table('vote_records', function (Blueprint $table) {
        $table->unique(['voter_id', 'election_event_id'], 'vote_records_voter_event_unique');
    });
}

public function down(): void
{
    Schema::table('vote_records', function (Blueprint $table) {
        $table->dropUnique('vote_records_voter_event_unique');
    });
}
```
Since the app-level check (`DiaD.php:198-210`) has been the *only* guard so far, duplicates are only possible if that check was raced — which is rare but exactly the risk being closed. **Before running this migration in Wave 0/1, add a defensive `SELECT voter_id, election_event_id, COUNT(*) FROM vote_records GROUP BY 1,2 HAVING COUNT(*) > 1` check** (or a small artisan command / migration guard) — if any real duplicates exist, they must be deduplicated (keep earliest `voted_at`) *before* adding the unique index, or the migration will fail outright. This is standard "check-then-add" practice for a unique index on a live table with data. **Confidence: HIGH.**

**Handling the resulting `QueryException` in Livewire (`DiaD.php::markVoted()`):** the existing app-level `VoteRecord::where(...)->first()` check remains the primary UX guard (fast-fail before touching storage/photo upload), but wrap the final `VoteRecord::create()` call in a try/catch for the DB-level race case:
```php
try {
    VoteRecord::create([...]);
} catch (\Illuminate\Database\QueryException $e) {
    if ((int) $e->getCode() === 23000) { // integrity constraint violation
        Notification::make()
            ->title('Este apoyo ya tiene un registro de voto en este evento (registrado simultáneamente)')
            ->warning()
            ->send();
        return;
    }
    throw $e;
}
```
**Confidence: HIGH** (standard Laravel MySQL/SQLite unique-violation code `23000` check pattern).

**Conflict rule for `markDidNotVote()`:** CONTEXT.md flags that marking "did not vote" doesn't check for/remove an existing evidence-backed `VoteRecord`. The fix is straightforward — before flipping status, check `VoteRecord::where('voter_id', $voter->id)->where('election_event_id', $activeEvent->id)->exists()` and either (a) block the "no votó" action with a clear message ("ya existe evidencia de voto, no se puede marcar como no votó sin antes anular el registro"), or (b) require an explicit confirmation + delete the conflicting `VoteRecord` transactionally. **This exact conflict-resolution UX (block vs. anulate-and-override) is a planning decision, not something research can resolve — flag as an Open Question for the planner/user.**

### 5. Filament 4 drill-through (REPT-04)

Two mechanisms, pick per-widget:

**A. Stat card → filtered list (`StatsOverviewWidget\Stat::make()->url()`):**
```php
Stat::make('Rezago de Validación', $backlogCount)
    ->description('Apoyos pendientes de validar')
    ->url(VoterResource::getUrl('index', [
        'tableFilters' => [
            'status' => ['values' => [VoterStatus::PENDING_REVIEW->value]],
```

The `tableFilters` array shape must match the filter's expected state key — for a `SelectFilter::make('status')->multiple()`, Filament's table filter state key is `values` (an array); for a single-value `SelectFilter`, the key is `value`. **Confidence: MEDIUM** — the `tableFilters` URL-param mechanism itself is well-documented community pattern (Filament v3, unchanged conceptually in v4), but the exact state-key naming (`value` vs `values`) should be spot-checked against this project's actual `VotersTable.php` filter definitions during implementation (its `status` filter is `->multiple()`, so `values` is the expected key).

**B. Table row → related record (`Table::recordUrl()`):** for widgets that are already tables (e.g., ranking tables), `->recordUrl(fn ($record) => VoterResource::getUrl('index', ['tableFilters' => ['registered_by' => ['value' => $record->id]]]))` on `TopLeadersTable` turns clicking a leader row into "show me all this leader's voters" — arguably higher-value than a single aggregate stat card, since `TopLeadersTable`/`TopCoordinatorsTable` are already per-row rankings.

**Don't hand-roll:** a custom query-string parser or a bespoke "filtered redirect" controller — Filament's resource `getUrl()` + `tableFilters` already round-trips correctly through `ListRecords`' table state hydration.

### 6. Queueing `FinalizeElectionEvent` (QUAL-02)

**Current:** `FinalizeElectionEvent::dispatchSync($event->id, $userId)` at `ManageElectionEvents.php:264` — already implements `ShouldQueue` (the job class itself is queue-ready; only the dispatch call is sync).

**Switch to real dispatch:**
```php
FinalizeElectionEvent::dispatch($event->id, $userId);
```
**User-facing tradeoff:** today, the coordinator/admin who deactivates the event waits synchronously for potentially thousands of `Voter` updates (chunked 500 at a time) to finish before the Filament page responds. Moving to `dispatch()` returns immediately, but the notification currently shown ("Evento desactivado") would no longer reflect "closure fully processed" — it would only mean "closure job was queued." **This requires either:** (a) a follow-up notification/event when the job completes (e.g., `Notification::make()->sendToDatabase($user)` inside the job's `handle()`, or a broadcast event the Livewire page listens for), or (b) accepting that the UI message changes to "Cierre en proceso, se notificará al finalizar." **This is a UX decision for the planner** — research confirms the mechanical switch is safe (job is idempotent-ish via `whereDoesntHave('voteRecords', ...)`, chunked, and campaign-scoped) but the completion-feedback design is not specified in CONTEXT.md and should be an explicit planning choice.

**Requires a running queue worker in every environment this runs in** (`QUEUE_CONNECTION=database` per `.env`) — `composer run dev` already starts `queue:listen --tries=1` locally, but production/staging must have a persistent `queue:work` (Supervisor, systemd, or Dokploy process) or the job will sit in `jobs` table forever. **Flag this as an Environment Availability item** — verify a queue worker process exists in whatever environment this phase's tests/deploy target before considering QUAL-02 "done."

**Structured logging (no new dependency):**
```php
// FinalizeElectionEvent::handle()
Log::info('election_event.finalize.started', ['election_event_id' => $this->electionEventId]);
// ... existing chunk logic ...
Log::info('election_event.finalize.completed', ['election_event_id' => $this->electionEventId, 'voters_closed' => $count]);
```
Add a `failed()` method to the job (standard `Illuminate\Contracts\Queue\ShouldQueue` job lifecycle hook) to log failures explicitly:
```php
public function failed(\Throwable $exception): void
{
    Log::error('election_event.finalize.failed', [
        'election_event_id' => $this->electionEventId,
        'error' => $exception->getMessage(),
    ]);
}
```
Same `Log::` pattern should be added at `DiaD.php:225` (photo-save failure, currently shown to user but never logged) and around `VoteRecord`/`markVoted`/`markDidNotVote` state transitions. **Confidence: HIGH** — this is vanilla Laravel job/log API, directly matches CLAUDE.md's "Log: `Log::info/error/debug`" convention.

**`failed_jobs` visibility:** table already exists via default Laravel migrations (confirm via `php artisan queue:failed` works) — no new table needed, just make sure `dispatch()` (not `dispatchSync()`) is used so failures actually land there instead of throwing inline and killing the request.

### 7. REPT-03 ownership/territory-scoped widgets — the biggest gap, and the core architecture pattern for this phase

**Existing precedent to mirror exactly** — `CallCenterStatsOverview.php`:
```php
$stats = $callCenterService->getReviewerStats(Auth::id());
```
No campaign-context indirection, no global scope reliance — straight `Auth::id()` into a service method. This is the pattern CONTEXT.md's discretion section explicitly asks to prefer, "given CAMP-05's queue-context finding."

**Ownership hierarchy already exists in the data model** (confirmed by reading `User.php`):
```php
// User.php — already present, no new migration needed
public function coordinator(): BelongsTo { return $this->belongsTo(User::class, 'coordinator_user_id'); }
public function leaders(): HasMany { return $this->hasMany(User::class, 'coordinator_user_id'); }
public function registeredVoters(): HasMany { return $this->hasMany(Voter::class, 'registered_by'); }
```
So: **a leader's own scope** = `Voter::where('registered_by', Auth::id())`. **A coordinator's team scope** = `Voter::whereIn('registered_by', Auth::user()->leaders()->pluck('id'))`.

**Recommended approach: new dedicated widget classes, not parameterized existing ones.** The admin-panel `TopLeadersTable`/`TerritorialDistributionChart`/`ValidationProgressChart` are registered in three different panel providers already (`AdminPanelProvider`, `CoordinatorPanelProvider`, `LeaderPanelProvider` all import the *same* widget classes today — that's the actual bug). Cloning into `CoordinatorTeamStatsOverview`/`LeaderTerritoryStatsOverview`-style classes (or, cheaper, adding a constructor-time scope check inside the *same* widget class based on `Auth::user()->hasRole(...)`) both work; given Filament widgets are stateless config classes registered per-panel already, the **lowest-risk change is to branch inside each existing widget's query method** on the current panel/role rather than creating parallel classes, since the panels already only register widgets they need — e.g.:

```php
// TopLeadersTable.php — inside table()
$activeCampaign = CampaignContext::currentCampaign();
$user = Auth::user();

$query = User::query()->when($activeCampaign, /* ...existing... */);

if ($user->hasRole('coordinator')) {
    $query->where('coordinator_user_id', $user->id); // only this coordinator's own leaders
} elseif ($user->hasRole('leader')) {
    // A leader's "leaders ranking" doesn't make sense — this widget likely shouldn't
    // even be registered in LeaderPanelProvider; reconsider whether leaders need
    // a "my own voters" widget instead of a leaderboard of leaders.
}
```

This surfaces an important nuance: **`TopLeadersTable` in `CoordinatorPanelProvider` needs coordinator-scoping (rank only their own leaders), but the same widget doesn't make sense at all in a leader's panel** (a leader isn't managing other leaders) — check whether `LeaderPanelProvider` even registers `TopLeadersTable` today (it currently does not — only `CoordinatorPanelProvider` does). `LeaderPanelProvider` registers `CampaignStatsOverview`, `ValidationProgressChart`, `TerritorialDistributionChart` — all three need to become "my own territory only" (filtered by `registered_by = Auth::id()` or the leader's assigned municipality/neighborhood) rather than campaign-wide.

**Don't hand-roll:** a generic polymorphic "scope resolver" class. Given only 2-3 widgets need this per panel, and the panels' roles are fixed and few (coordinator, leader), explicit `hasRole()` branches inside each widget (as `CallCenterStatsOverview` already demonstrates for reviewers) is simpler, more testable, and matches the existing codebase's style better than a new abstraction.

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Maintenance mode flag storage | Custom DB/cache "kill switch" flag + custom middleware check on every request | Laravel's native `php artisan down`/`up` (file-based flag, already framework-integrated) | Already handles bypass secrets, custom 503 views, retry-after headers — reinventing loses all of that for free |

## Common Pitfalls

### Pitfall 1: CAMP-05's `withoutGlobalScopes()` audit — don't just "add a filter," verify the *existing* filter is actually explicit and complete
**What goes wrong:** Assuming `withoutGlobalScopes()` call sites are dangerous by default and wrapping them in a "fix," when 2 of the 3 (`DuplicatesReportTable`, `DuplicatesExport`, `VoterDuplicateAssignmentService`) are the *intentionally* cross-campaign duplicate-detection mechanism (REPT-01's documented sole exception) — CONTEXT.md explicitly says these are fine.
**Why it happens:** Grepping for `withoutGlobalScopes` surfaces both the intentional exception (duplicates) and the three CONTEXT.md actually wants audited (`VoterResource.php:69`, `SurveyResource.php:65`, `CampaignResource.php:80`).
**How to avoid:** Only inspect the 3 named Resource-level call sites; confirm each has its own explicit `->where('campaign_id', ...)` immediately re-applied after the scope removal. Do not touch `DuplicatesReportTable`/`DuplicatesExport`/`VoterDuplicateAssignmentService` — those are the confirmed-intentional REPT-01 exception.
**Warning signs:** If a "fix" changes behavior in the duplicates report/export, that's a regression, not a fix.

### Pitfall 2: DAYD-03's unique index migration failing on existing duplicate data
**What goes wrong:** Running `$table->unique(['voter_id','election_event_id'])` against a live table that already has a duplicate pair fails the migration outright in production.
**Why it happens:** The app-level check has been racy, not absent — low probability but nonzero chance of an existing duplicate.
**How to avoid:** Add a pre-migration verification step (raw query or artisan command) that asserts zero duplicate `(voter_id, election_event_id)` pairs exist; if any are found, resolve them (keep the earliest `voted_at`, or flag for manual review) before the unique-index migration runs.
**Warning signs:** Migration fails with "Duplicate entry ... for key" on deploy.

### Pitfall 3: QUAL-02's `dispatch()` switch changing perceived behavior without a queue worker running
**What goes wrong:** Switching `dispatchSync()` → `dispatch()` in code but the target environment has no persistent `queue:work` process — the job sits in the `jobs` table forever, and "closing an election event" silently never finalizes voter statuses.
**Why it happens:** `composer run dev` conveniently runs `queue:listen` locally, masking the fact that production needs its own always-on worker process.
**How to avoid:** Before switching to real `dispatch()`, confirm (or add as an explicit task) that a supervised queue worker exists in every deployment target. Flagged in Environment Availability below.
**Warning signs:** `php artisan queue:failed` and the `jobs` table both stay empty/growing with no completion — the job never actually ran.

### Pitfall 4: OTP for a public/unauthenticated flow can't use session-based or `Auth::id()`-scoped storage
**What goes wrong:** Building the OTP check against `Auth::user()` or Laravel session state, which doesn't exist reliably for the public `registro/{token}` flow (unauthenticated visitors, possibly on shared devices/links).
**Why it happens:** Most Laravel OTP tutorials assume an authenticated context (e.g., 2FA for a logged-in user) — this flow is the opposite: pre-authentication, invitation-token-scoped.
**How to avoid:** Scope OTP records by `phone` + `campaign_id` (derived from the `Invitation`), not by session/user, and expire aggressively (5-10 min) since the "identity" being verified is just a phone number, not an account.

### Pitfall 5: Confusing "leader registration" with user-account registration
**What goes wrong:** Building OTP into `resources/views/livewire/auth/register.blade.php` (the Fortify user-account registration form) instead of `PublicVoterRegistrationController` (the actual "a leader's shared link lets a voter self-register" flow).
**Why it happens:** The phrase "leader registration" is ambiguous without codebase inspection — it could mean "registering a new leader user" or "the registration flow that a leader's invitation link enables."
**How to avoid:** Direct inspection confirms `registro/{token}` (invitation-gated, public, creates a `Voter`, not a `User`) is the only registration flow without existing verification and the only one matching "no code generation/storage/verification, no wiring into leader registration" from CONTEXT.md. **Flagged as an Open Question below for explicit confirmation before planning, since this is a client-requested feature and getting the target flow wrong wastes a full implementation cycle.**

## Open Questions

1. **Which flow is "leader registration" for the OTP feature?**
   - What we know: `PublicVoterRegistrationController`/`registro/{token}` is the only unauthenticated, invitation-driven registration flow matching CONTEXT.md's description ("no wiring into leader registration," "nothing exists").
   - What's unclear: whether the client actually means this voter self-registration flow, or a different flow for onboarding new *leader/coordinator user accounts* (the `Invitation` model does support `target_role: LEADER/COORDINATOR` for user-account invitations too, via `coordinator.create-leader`).
   - Recommendation: confirm with the user/client before planning task breakdown — if it's the voter self-registration flow, the plan targets `PublicVoterRegistrationController`; if it's leader/coordinator account onboarding, the plan targets wherever `coordinator.leaders.create` issues its invitation. Given the phrase "no wiring into leader registration" plus "no code generation/storage/verification exists at all," the public voter self-registration flow is the stronger-evidence interpretation, but this should be a 30-second confirmation before implementation, not an assumption baked into the plan.

2. **QUAL-02's dispatch-to-queue completion feedback design**
   - What we know: switching to `dispatch()` is mechanically safe; the job itself needs no changes to be queue-safe.
   - What's unclear: what the user sees between "clicked deactivate" and "closure job actually finished" — silence, a spinner, a follow-up notification?
   - Recommendation: default to a simple "cierre en proceso, se notificará cuando termine" message plus a Filament database notification (`Notification::make()->sendToDatabase($user)`) dispatched from inside the job's `handle()` on completion — cheap, no new infra, consistent with Filament's built-in notification bell.

3. **Kill switch's super-admin-bypass mechanism (`MaintenanceModeException` render-null vs middleware-priority vs `--secret`)**
   - What we know: all three approaches exist in Laravel's toolkit; the `--secret` flag is the only one with rock-solid official documentation.
   - What's unclear: whether returning `null` from a `MaintenanceModeException` render closure actually resumes normal (non-maintenance) request handling in this Laravel version, without further wiring.
   - Recommendation: prototype this specific behavior first (cheap, ~15 min manual test: `php artisan down`, hit a route as super admin vs. as a normal user) before committing to it in the plan; fall back to the documented `--secret` bypass link (stored/bookmarked by super admins) if the exception-render approach doesn't cleanly bypass.
