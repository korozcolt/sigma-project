# Phase 05.1 Plan 04: Voter Census Validation Trigger, Profile Guidance & Contact-State Filter Summary

**Census validation is now operator-triggerable from the Voters table with an auditable ValidationHistory trail, and a voter's profile surfaces validation source, next recommended action, and missing-data gaps.**

## Performance

- **Duration:** 70 min

- **Completed:** 2026-07-23T20:09:00Z
- **Tasks:** 3
- **Files modified:** 5 (3 app files, 2 pre-existing test files fixed for a regression) + 2 new test files

## Accomplishments
- `VoterValidationService::updateVoterStatus()` now writes an auditable `ValidationHistory` row (`validation_type=census`, `previous_status`, `new_status`, `validated_by=Auth::id()`) on every census validation, found or rejected
- Operators can trigger census validation directly from a Voters table row via a new `validateCensus` action, with a success notification
- Operators can filter the Voters table by contact state: has an open call assignment, has a completed survey response, or has no contact at all
- A voter's profile page now shows census-validation status/source, a plain-language next recommended action derived from current status, and a missing-key-data summary (phone/email/neighborhood/birth_date)

## Decisions Made
- Reordered `actingAs()` in the new census-validation test to occur *after* fixture `Voter`/`CensusRecord` creation but *before* the service call — creating the acting-as user first (or acting as a non-super-admin with no campaigns) would make `Voter::factory()->create()` throw via `CampaignContext::enforceCampaignId()`, since that hook forcibly reassigns `campaign_id` to the current campaign context whenever a campaign context exists, and throws when none exists for a non-super-admin authenticated user.
- Fixed the same ordering issue in the two pre-existing `VoterValidationServiceTest` files rather than leaving them broken, since they now legitimately need an authenticated actor for `validated_by` to satisfy the non-nullable foreign key — this is a direct, in-scope consequence of Task 1's change (Rule 1: auto-fix bugs caused by the current task).
- `missingDataSummary()` includes both `email` and `birth_date` per the plan's exact code, after confirming both are real, nullable `Voter` columns in `database/migrations/2025_11_03_132954_create_voters_table.php`.
- The plan's Task 3 acceptance criteria expected `grep -c "TextEntry::make"` to return 11; the plan's own given code (used verbatim) actually produces 12 (8 original + 4 new: `census_validated_at`, `last_validation_source`, `next_step`, `missing_data`). This is a minor miscount in the plan text itself, not a deviation in the implementation — the substantive criterion ("more than 8 entries") is satisfied.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Fixed two pre-existing test files broken by Task 1's ValidationHistory write**
- **Found during:** Task 1 (VoterValidationService writes an auditable ValidationHistory entry)
- **Issue:** `updateVoterStatus()` now always calls `ValidationHistory::create(['validated_by' => Auth::id(), ...])`. `validation_histories.validated_by` is a required (non-nullable) foreign key. The pre-existing tests in `tests/Feature/VoterValidationServiceTest.php` and `tests/Feature/Services/VoterValidationServiceTest.php` called `updateVoterStatus()`/`validateAndUpdate()`/`validatePendingVoters()` without any authenticated user, which would now insert `validated_by = null` and fail the DB constraint.
- **Fix:** Added `actingAs(User::factory()->create())` in each affected test, placed immediately before the service-method call (after all `Voter`/`CensusRecord` fixture data was already created, to avoid triggering `CampaignContext::enforceCampaignId()` failures on `Voter::factory()->create()` for a non-super-admin actor with no campaign).
- **Files modified:** `tests/Feature/VoterValidationServiceTest.php`, `tests/Feature/Services/VoterValidationServiceTest.php`
- **Verification:** `php artisan test --filter=VoterValidationServiceTest` (11/11 passing), full `composer test` suite green (840/840)
- **Committed in:** `15aa585` (Task 1 commit)

**2. [Rule 3 - Blocking] Worktree environment setup: real `composer install` + `npm run build`**
- **Found during:** Task 1, before any test could run
- **Issue:** This worktree had no `vendor/`, no `.env`, and no `public/build/` assets. A sibling worktree had already symlinked `vendor/` to the main repo, which I initially followed — but that caused `Illuminate\Foundation\Application::inferBasePath()` to resolve to the *main repo's* absolute path (via Composer's `ClassLoader::getRegisteredLoaders()` key), leaving `$this->app` null in every Pest/PHPUnit test (silent `Container::getInstance()` fallback to a bare `Container`, `Model::$resolver` never set).
- **Fix:** Removed the `vendor` symlink and ran a real `composer install` (using the existing `composer.lock`) so Composer's autoloader registers with this worktree's own real path. Copied `.env` from the main repo (same DB-less sqlite `:memory:` testing config either way). Symlinked and later confirmed via `npm run build` (real, not symlinked `node_modules`, since it was already available) that `public/build/manifest.json` exists, which is required by any route rendering the full app layout (auth pages, dashboards) — these are unrelated to this plan's scope but were needed for a genuinely green `composer test` full-suite run.
- **Files modified:** none tracked (vendor, .env, node_modules, public/build are all gitignored)
- **Verification:** `composer test` → 840 passed, 0 failed (previously 26-27 unrelated failures, all `ViteManifestNotFoundException`, before the build step)
- **Committed in:** n/a (environment setup only, no tracked files changed)
