- Every role/campaign-scope/cross-campaign denial now surfaces a distinct, human-readable Spanish message naming the actual reason instead of a generic "unauthorized"/"no permission" string

- Found and fixed a test-isolation bug introduced by this task's own new tests (leftover `CampaignContext` static override state leaking into unrelated test files) before it could destabilize the full suite

- **Files modified:** none tracked (vendor/, node_modules/, .env, public/build/ are all gitignored)
- **Verification:** `php artisan about` and a full `composer test` run both succeeded afterward

**2. [Rule 1 - Bug] Pre-existing `RoleMiddlewareTest` assertion broke on the new `AuthorizationException` behavior**
- **Found during:** Task 1 verification
- **Issue:** `tests/Feature/Middleware/RoleMiddlewareTest.php`'s "denies access when user does not have required role" test asserted `Symfony\Component\HttpKernel\Exception\HttpException`, which the middleware no longer throws (it now throws `Illuminate\Auth\Access\AuthorizationException`, required by this task's PERM-02 fix)
- **Fix:** Updated the test's `expectException`/`throws()` calls to `AuthorizationException::class`
- **Files modified:** `tests/Feature/Middleware/RoleMiddlewareTest.php`
- **Verification:** `vendor/bin/pest --filter=RoleMiddlewareTest` — 16/16 green
- **Committed in:** `b10d2d7` (part of Task 1 commit)

**3. [Rule 1 - Bug] `Voter::factory()->make()` in the new test unexpectedly triggered a real DB write and threw before reaching the test's own assertion**
- **Found during:** Task 1, writing `OperationalDenialMessagesTest.php`
- **Issue:** `VoterFactory`'s `neighborhood_id` attribute falls back to `Neighborhood::factory()` when no neighborhood row exists; Eloquent factories eagerly `create()` nested factory *values* even when the parent is only `make()`d. Since `Neighborhood` uses `HasCampaignContext`, that eager create fired `enforceCampaignId()` — the very method under test — outside the test's own `try`/`catch`, masking the real assertion as a random ~30%-flaky "uncaught exception"
- **Fix:** Replaced `Voter::factory()->make()` with a plain `new Voter` instance in that specific test (the model instance's attributes aren't touched by `enforceCampaignId()`'s null-context branch, so no factory-time side effects are needed)
- **Files modified:** `tests/Feature/OperationalDenialMessagesTest.php`
- **Verification:** `vendor/bin/pest --filter=OperationalDenialMessagesTest` — 3/3 green, reproducibly (previously ~30% flaky)
- **Committed in:** `b10d2d7`

**4. [Rule 1 - Bug] New tests calling `CampaignContext::setCampaignId()` leaked static state into unrelated test files, destabilizing the full suite**
- **Found during:** Post-Task-3 full-suite regression run (`composer test`)
- **Issue:** `CampaignContext::setCampaignId()` mutates `private static` properties that persist for the entire PHPUnit/Pest process, not per-test. `OperationalDenialMessagesTest` and `CampaignScopeAuditTest` set a real campaign override and never reset it, so whichever unrelated test file Pest ran next inherited a stale campaign context — surfacing as ~26 intermittent failures across `DashboardWidgetsTest`, `TopCoordinatorsTableTest`, `SurveyResourceTest`, and others (confirmed against a clean pre-task baseline run in a scratch worktree, which showed only the one pre-existing, already-documented `UserResourceTest` flake)
- **Fix:** Added a reflection-based `afterEach()` in both new test files that resets `CampaignContext`'s `overrideCampaignId`/`overrideMode` static properties to `null` after every test
- **Files modified:** `tests/Feature/OperationalDenialMessagesTest.php`, `tests/Feature/CampaignScopeAuditTest.php`
- **Verification:** `composer test` run twice consecutively — 843/843 green both times (previously 27 and 26 failed on two consecutive runs of the same uncommitted state)
- **Committed in:** `497ff8b`

- Discovered and fixed a genuine test-isolation footgun in how `CampaignContext::setCampaignId()` is used in tests project-wide (its static properties are never reset between test files); this task fixed its own two new test files but did **not** retrofit the several pre-existing test files that call `setCampaignId()` without resetting (`IsElectionDayMiddlewareTest`, `UserResourceTest`, and the `E2E/ChromeDevTools/*` suite) — that broader cleanup is out of this task's scope and is logged as a pending follow-up below

## Pending Follow-Up (out of this task's scope)

- `IsElectionDayMiddlewareTest.php`, `Filament/UserResourceTest.php`, and the `tests/E2E/ChromeDevTools/*` suite all call `CampaignContext::setCampaignId()` in `beforeEach()` without resetting the static override afterward. This didn't destabilize the baseline suite (each file's own `beforeEach` happens to mask it for its own tests), but it is latent test-pollution risk for any future test file that assumes a clean `CampaignContext` state. Worth a dedicated cleanup pass (e.g., a shared Pest `afterEach` in `tests/Pest.php`, or a public `CampaignContext::resetForTesting()` helper) in a future hardening plan.
