## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking issue] Fixed cross-campaign test fixture in ApoyosLideresCoordinadoresTableTest**
- **Found during:** Task 2 (running `php artisan test tests/Feature/Filament/ApoyosLideresCoordinadoresTableTest.php`)
- **Issue:** The test created `$otherVoter` with an explicit `'campaign_id' => $otherCampaign->id` while the session's active campaign context still pointed at `$this->campaign`. `App\Services\CampaignContext::enforceCampaignId()` (invoked on every `Voter` `creating` event via the `HasCampaignContext` trait) unconditionally overwrites `campaign_id` with the currently active session campaign whenever one is set — confirmed via `php artisan tinker` that `$otherVoter->fresh()->campaign_id` ended up equal to `$this->campaign->id`, not `$otherCampaign->id` as the test intended. This meant the widget's campaign-scoping was correctly implemented, but the test's own fixture never actually produced a cross-campaign voter to exclude, so `assertCanNotSeeTableRecords([$otherVoter])` failed regardless of implementation correctness.
- **Fix:** Switched `campaign_context.campaign_id`/`mode` in the session to `$otherCampaign` immediately before creating `$otherVoter`, then switched back to `$this->campaign` before mounting the widget — the exact same session-switch-then-restore pattern the sibling `DuplicatesReportTableTest` (D-06, plan 04.1-01) already uses for its own cross-campaign fixtures.
- **Files modified:** `tests/Feature/Filament/ApoyosLideresCoordinadoresTableTest.php`
- **Commit:** `28b86f3`

No architectural changes were needed; this was a test-fixture-only fix that did not touch `CampaignContext` or any other shared service.
