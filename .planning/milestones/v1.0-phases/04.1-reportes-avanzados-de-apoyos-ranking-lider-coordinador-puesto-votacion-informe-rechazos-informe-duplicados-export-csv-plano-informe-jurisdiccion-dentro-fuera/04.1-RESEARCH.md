## User Constraints (from CONTEXT.md)

### Locked Decisions

**Definición de "apoyo válido" para conteos y rankings**
- **D-01:** Los conteos y rankings (líderes, coordinadores) EXCLUYEN apoyos en estado `DUPLICATE` — solo cuentan los apoyos válidos/asignados. El informe de duplicados (separado, ítem 4) sí muestra todos los apoyos incluyendo los duplicados en disputa.

**Formato de entrega**
- **D-02:** Los 6 reportes son widgets de dashboard con botón de exportar (CSV/Excel) en cada uno — un solo lugar de verdad por reporte, siguiendo el patrón ya usado por `TopLeadersTable`. No hay reportes "solo descargables" sin vista de dashboard.

**Alcance del CSV plano masivo**
- **D-03:** El CSV plano combina Apoyos + Líderes + Coordinadores: una fila por apoyo, con columnas aplanadas de los datos de su líder y coordinador (nombre, teléfono, etc.). NO incluye llamadas, encuestas, mensajes u otras tablas operativas en esta fase.

**Informe de jurisdicción en campañas nacionales**
- **D-04:** Cuando la campaña es de alcance nacional (`Campaign.municipality_id` y `department_id` ambos null), el informe de jurisdicción NO aplica — se oculta o muestra un mensaje explicando que no aplica, en vez de intentar inferir un territorio de referencia.

### Claude's Discretion
- Diseño exacto de columnas del CSV combinado (nombres, orden, más allá de lo ya fijado para apoyos en Fase 02.1).
- Mecánica exacta del botón de exportar en cada widget (acción de tabla vs. botón de header vs. Filament export action).
- Lógica exacta de agregación para el ranking de "puestos de votación" (agrupar por `polling_place_id`).
- Si se incluye o no el "índice de calidad de dato" (%válidos/%duplicados/%fuera de jurisdicción) como KPI adicional.

### Deferred Ideas (OUT OF SCOPE)
- Mapa de calor por puesto de votación (visualización geográfica) — requiere geodatos que el sistema no tiene hoy.
- Delegar el import masivo de apoyos a coordinadores — fuera de alcance de esta fase de reportes.

## Summary

This phase adds six new reporting surfaces on top of data structures that already exist and are already correctly written to — Phase 02.1 completed the `duplicate_sequence`/`DUPLICATE` schema, `Gremio`/`Subcategoria` catalogs, and the Apoyo rename. Nothing here requires new tables, new enum values, or new business logic for data capture. The work is entirely: (1) new Filament v4 `TableWidget` classes for aggregation/ranking, (2) one `Voter`-status/`CallResult` consolidation query for rejections, (3) one `document_number`-grouped query for duplicates (reusing the exact service already built in `VoterDuplicateAssignmentService`), (4) one comparison query for jurisdiction dentro/fuera, and (5) one combined `maatwebsite/excel` export class for the flat CSV.

The existing `TopLeadersTable` widget is the direct pattern to clone, but it currently has **no DUPLICATE exclusion** — `withCount(['registeredVoters' => ...->where('campaign_id', ...)])` counts every status. This is the concrete bug/gap D-01 requires fixing, and it must be fixed in the existing widget (not just avoided in new ones), since D-01 says rankings must exclude duplicates project-wide. Filament v4's `TableWidget` fully supports `->headerActions([Action::make('export')->action(fn () => $export->download(...))])` (verified in `vendor/filament/tables/src/Concerns/InteractsWithTable.php` and `Table/Concerns/HasHeaderActions.php`), which is exactly the "one Action closure returns `$export->download()`" pattern already used in `app/Filament/Resources/Voters/Pages/ListVoters.php`. This means D-02 (widget + export button, same place) is achievable with zero new architecture — every new widget's `table()` method just adds a `->headerActions([...])` export button using the same `maatwebsite/excel` `FromQuery`/`WithMapping` export classes already established for Voters/Leaders/Coordinators.

**Primary recommendation:** Build all six reports as `Filament\Widgets\TableWidget` subclasses (even the "jurisdiction" and "líderes+apoyos por coordinador" ones, which read more like dashboards) so every report gets the same `->headerActions()` export button mechanism for free and matches D-02's "one Action, one place" rule uniformly. Reuse `maatwebsite/excel`'s `FromCollection`/`FromQuery` + `WithMapping` + `WithHeadings` pattern already established in `app/Exports/*.php` for every new export, including the combined flat CSV.

### Pattern 1: Widget + inline export button (D-02)
**What:** A `TableWidget::table()` method that both defines the ranking/report query AND registers a `headerActions()` export `Action` that reuses the same query to build the export.
**When to use:** Every one of the 6 reports.
**Verified in this codebase:**
```php
// Source: app/Filament/Resources/Voters/Pages/ListVoters.php (existing pattern)
Action::make('export')
    ->label('Exportar')
    ->icon('heroicon-o-arrow-down-tray')
    ->action(function () {
        return (new VotersExport(...))->download('apoyos.xlsx');
    })
```
```php
// Source: vendor/filament/tables/src/Table/Concerns/HasHeaderActions.php — confirms
// Table (used by TableWidget::table()) supports ->headerActions([...]) identically
// to a Filament Resource's ListRecords page.
public function headerActions(array|ActionGroup $actions, HeaderActionsPosition|Closure|null $position = null): static
```
This means each new report widget can be:
```php
class TopCoordinatorsTable extends TableWidget
{
    public function table(Table $table): Table
    {
        return $table
            ->query(fn (): Builder => /* ranking query */)
            ->headerActions([
                Action::make('export')
                    ->label('Exportar')
                    ->icon('heroicon-o-arrow-down-tray')
                    ->action(fn () => (new TopCoordinatorsExport(...))->download('ranking-coordinadores.xlsx')),
            ])
            ->columns([...]);
    }
}
```

### Pattern 2: Campaign-scoped aggregation query
**What:** Every widget must resolve `CampaignContext::currentCampaign()` and scope the query to it (or handle "no active campaign" gracefully, as `TerritorialDistributionChart` does by returning empty datasets).
**Verified in this codebase:** `TopLeadersTable` and `TerritorialDistributionChart` both call `CampaignContext::currentCampaign()` at the top of their query-building method and either `->when($activeCampaign, ...)` or early-return empty data if null.
**Example (rejections report query, following the same shape):**
```php
$activeCampaign = CampaignContext::currentCampaign();

Voter::query()
    ->when($activeCampaign, fn ($q) => $q->where('campaign_id', $activeCampaign->id))
    ->where(function ($q) {
        $q->whereIn('status', [VoterStatus::REJECTED_CENSUS->value, VoterStatus::CORRECTION_REQUIRED->value])
          ->orWhereHas('verificationCalls', fn ($q2) => $q2->whereIn('call_result', [
              CallResult::REJECTED->value, CallResult::INVALID_NUMBER->value, CallResult::NOT_INTERESTED->value,
          ]));
    });
```

### Pattern 3: D-01 exclusion — fixing `TopLeadersTable`
**Current (buggy per D-01) query in `TopLeadersTable::table()`:**
```php
->whereHas('registeredVoters', fn ($q) => $q->where('campaign_id', $activeCampaign->id))
->withCount(['registeredVoters' => fn ($q) => $q->where('campaign_id', $activeCampaign->id)])
```
**Required fix — add a status exclusion to both the `whereHas` and the `withCount` closures:**
```php
->whereHas('registeredVoters', fn ($q) => $q->where('campaign_id', $activeCampaign->id)
    ->where('status', '!=', VoterStatus::DUPLICATE->value))
->withCount(['registeredVoters' => fn ($q) => $q->where('campaign_id', $activeCampaign->id)
    ->where('status', '!=', VoterStatus::DUPLICATE->value)])
```
This same exclusion must be replicated in the new coordinator ranking and polling-place ranking (D-01 says "rankings" plural — líderes AND coordinadores; polling-place ranking is a Claude's Discretion item but should follow the same "valid apoyo" definition for consistency).

### Pattern 4: Coordinator ranking — two valid aggregation strategies
`coordinator_user_id` lives on `User`, not on `Voter`. A "ranking de coordinadores" has two possible readings, and CONTEXT.md does not disambiguate — this is a planning decision point (see Open Questions):
- **(a) Direct apoyos registered by the coordinator personally** — same shape as `TopLeadersTable`, just `->role('coordinator')` instead of `->role('leader')` (mirrors `CoordinatorsExport`'s existing `voters_count` pattern: `$coordinator->registeredVoters()->count()`).
- **(b) Apoyos registered by all leaders under that coordinator** (sum across `coordinator->leaders()->registeredVoters()`) — requires a subquery/join through `users.coordinator_user_id`, e.g.:
```php
User::query()->role('coordinator')
    ->withCount(['leaders as apoyos_equipo_count' => function ($q) use ($activeCampaign) {
        $q->join('voters', 'voters.registered_by', '=', 'users.id')
          ->where('voters.campaign_id', $activeCampaign->id)
          ->where('voters.status', '!=', VoterStatus::DUPLICATE->value);
    }]);
```
Given the phase also asks for a separate "informe de líderes+apoyos por coordinador" (item 1) that explicitly shows meta vs. real per coordinator with their leaders' apoyos, reading (b) — team rollup — is almost certainly what's wanted for item 1, while the coordinator "ranking" (item 2) most likely means the same team-rollup number used for sorting. Plan should treat item 1 and item 2's "coordinator ranking" as closely related/derivable from the same aggregation, to avoid building two divergent definitions of "a coordinator's apoyos."

### Pattern 5: Polling-place ranking
`Voter::polling_place_id` is a plain FK column (not computed at query time — populated once at data-entry time via the `HasRegistraduriaPolling` Livewire concern in `EditVoter`/`CreateVoter`). This means the ranking query is a straightforward `groupBy('polling_place_id')` + join to `polling_places`, exactly mirroring `TerritorialDistributionChart`'s municipality aggregation:
```php
Voter::query()
    ->select('polling_places.name', DB::raw('COUNT(*) as total'))
    ->join('polling_places', 'voters.polling_place_id', '=', 'polling_places.id')
    ->where('voters.campaign_id', $activeCampaign->id)
    ->where('voters.status', '!=', VoterStatus::DUPLICATE->value)
    ->groupBy('polling_places.id', 'polling_places.name')
    ->orderByDesc('total');
```
Voters with a `null` polling_place_id (not yet resolved via Registraduría lookup) will be silently excluded by the inner join — this is correct behavior but worth surfacing as a caveat/footnote in the widget (e.g., "N apoyos sin puesto de votación asignado").

### Pattern 6: Duplicates report — exact schema confirmed
Per `docs/REGLAS_NEGOCIO.md` §2 and `app/Filament/Resources/Voters/Pages/EditVoter.php`'s `reassignDuplicateOwner` action:
- Group by `document_number`. `VoterDuplicateAssignmentService::siblingsFor($documentNumber)` already does this exact grouping (`Voter::withoutGlobalScopes()->withTrashed()->where('document_number', $documentNumber)->orderBy('duplicate_sequence')->get()`) — reuse this service rather than re-deriving the query.
- Each sibling row has: `status` (`DUPLICATE` for losers, `PENDING_REVIEW` for the reassigned winner, or original status for `-0` never-disputed), `duplicate_sequence` (immutable, display via `Voter::getDisplaySuffixAttribute()` → `"{$document_number}-{$duplicate_sequence}"`), `registeredBy` (líder/coordinador), and — for the líder's coordinator — `registeredBy->coordinator` (via `User::coordinator()` belongsTo).
- Reassignment audit trail: `ValidationHistory` rows with `validation_type = 'duplicate_reassignment'`, `notes` containing the admin's free-text reason plus a bracketed suffix (`"[Registro confirmado como dueño legítimo de la cédula]"` or `"[Registro marcado como duplicado tras la reasignación]"`).
- **The report's natural grouping unit is `document_number`, not individual `Voter` rows** — the widget should probably show one row per document_number-group with an expandable/nested list of siblings, OR flatten to one row per Voter with a repeated document_number column and a "es el dueño actual" boolean (`status !== DUPLICATE`). Table structure (flattened vs. grouped) is a Claude's Discretion item within Filament's normal table capabilities — no Filament limitation blocks either approach, but flattening (one row per Voter, matching D-02's "table = source of truth" spirit and being trivially exportable) is simpler to implement and to reconcile against `REPT-01` ("counts reconcile to source records").
- Since duplicates by definition span campaigns (`VoterDuplicateAssignmentService` explicitly bypasses campaign global scopes — "duplicates registered under other campaigns" per the STATE.md bugfix note in 02.1-10), **the duplicates report is one of the few report surfaces that may need to intentionally NOT scope by the active campaign**, or must clearly label the campaign each sibling belongs to when siblings span campaigns. This is a deliberate exception CONTEXT.md doesn't explicitly call out (its "Established Patterns" section says campaign isolation applies "except where the report itself explicitly crosses campaigns, which does not apply here" — but the duplicates report is the one place where cross-campaign duplicate siblings are a known, tested phenomenon per 02.1-10's bugfix). **Flag this for the plan to resolve explicitly** (see Open Questions).

### Pattern 7: Jurisdiction dentro/fuera — exact comparison + hide condition
`Campaign` has `municipality_id`, `department_id`, and a `scope` cast to `CampaignScope` enum (`Nacional`/`Departamental`/`Municipal`/`Regional`). Critically, `Campaign::boot()`'s `saving()` hook **already guarantees** `municipality_id` and `department_id` are both forced to `null` exactly when `scope === CampaignScope::Nacional` (and `municipality_id` is forced null when `scope === Departamental`). This means:
- **D-04's hide condition can be implemented either as `$campaign->scope === CampaignScope::Nacional` OR as `is_null($campaign->municipality_id) && is_null($campaign->department_id)` — they are guaranteed equivalent by the model's own `saving()` hook.** Prefer the `scope === Nacional` check for readability/intent-clarity, since it directly expresses "national campaigns don't have a jurisdiction report" rather than relying on a null-coincidence.
- Comparison query: a `Voter` is "dentro" if `voter.municipality_id === campaign.municipality_id` (municipal-scope campaigns) or `voter.municipality->department_id === campaign.department_id` (departmental-scope campaigns, since `Voter` has no direct `department_id` column — confirmed: `Voter::$fillable` has `municipality_id`/`neighborhood_id`/`polling_place_id` but no `department_id`; department must be resolved via `Municipality::department_id`, requiring a join or `Voter::municipality.department_id`).
```php
// Municipal-scope campaign:
Voter::where('campaign_id', $campaign->id)
    ->selectRaw('CASE WHEN municipality_id = ? THEN "dentro" ELSE "fuera" END as jurisdiccion', [$campaign->municipality_id])
    ->groupBy('jurisdiccion');

// Departmental-scope campaign (Voter has no department_id column — must join Municipality):
Voter::where('voters.campaign_id', $campaign->id)
    ->join('municipalities', 'voters.municipality_id', '=', 'municipalities.id')
    ->selectRaw('CASE WHEN municipalities.department_id = ? THEN "dentro" ELSE "fuera" END as jurisdiccion', [$campaign->department_id])
    ->groupBy('jurisdiccion');
```
- `Regional` scope campaigns are a third case not explicitly covered by D-04 (which only mentions Nacional as the hide condition) — `Campaign::boot()` does NOT null out `municipality_id`/`department_id` for `Regional` scope, so a Regional campaign could have either set or both null depending on how it was created. Recommend treating Regional the same as whichever of municipality_id/department_id is actually populated (fall back to department-level comparison if only `department_id` is set), and hide only when truly both null — this is functionally identical to D-04's stated rule, just extended to cover the one scope D-04's example didn't enumerate.

### Anti-Patterns to Avoid
- **Don't recompute `polling_place_id` or duplicate detection at report time.** Both are already resolved/written at data-entry time (Registraduría lookup, `Voter::booted()` `creating` hook). Reports are read-only aggregations over already-correct data — resist the urge to add "smarter" inference logic in the reporting layer.
- **Don't build a new campaign-scoping mechanism.** Every new widget/export must call `CampaignContext::currentCampaign()` exactly like the 3 existing widgets do — do not introduce a parallel scoping helper.
- **Don't silently drop cross-campaign duplicate siblings from the duplicates report** by applying the default campaign global scope — this would silently produce an incomplete/misleading report for the one entity type (duplicates) that is explicitly known to span campaigns (per the 02.1-10 bugfix note in STATE.md).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Finding all rows sharing a `document_number` | A new grouping query | `VoterDuplicateAssignmentService::siblingsFor($documentNumber)` (existing, tested, campaign-scope-safe) | Already handles `withoutGlobalScopes()->withTrashed()` correctly per the 02.1-10 bugfix; reinventing risks reintroducing that exact bug |
| Excel/CSV file generation | Raw `fputcsv` streaming (used once in `ListVoters.php`'s `duplicatesReport` action for a narrow use case) | `maatwebsite/excel`'s `FromQuery`/`FromCollection` + `WithMapping` + `WithHeadings` + `ShouldAutoSize` + `WithStyles`, matching `VotersExport`/`LeadersExport`/`CoordinatorsExport` | Consistency with all 5 existing export classes; gets auto-sizing, header styling, and `.xlsx` support for free |
| Dashboard widget export button | A custom Livewire download route/controller | Filament `Action::make(...)->action(fn () => $export->download(...))` inside `->headerActions([...])` on the widget's `Table` | Exact pattern already proven working in `ListVoters.php`; `Table` (used inside `TableWidget`) supports `headerActions()` identically to a resource list page |

**Key insight:** Every "hard part" of this phase (duplicate grouping, campaign scoping, export mechanics) was already solved correctly in Phase 02.1 or in the existing widget/export files. The actual net-new work is assembling new queries and columns on top of proven plumbing — this is a low-risk, mechanical phase as long as the D-01 exclusion fix is applied consistently everywhere a "valid apoyo" count is shown.

## Common Pitfalls

### Pitfall 1: Forgetting the D-01 exclusion in the NEW rankings (not just fixing the old one)
**What goes wrong:** Cloning `TopLeadersTable` for coordinators/polling-places without also adding the `status != DUPLICATE` exclusion in the clone.
**Why it happens:** The existing widget being cloned doesn't have this exclusion today, so a naive clone reproduces the same gap.
**How to avoid:** Every new ranking widget's query must explicitly filter/exclude `VoterStatus::DUPLICATE`, and every widget test must include a case with a duplicate voter asserting it's excluded from the count (mirroring `tests/Feature/DashboardWidgetsTest.php`'s existing `top leaders table does not show users without voters` style test).
**Warning signs:** A ranking count that's higher than expected once duplicate test data is seeded.

### Pitfall 2: Conflating "informe de duplicados" scope with campaign isolation
**What goes wrong:** Applying the default `campaign_id` filter to the duplicates report and silently hiding cross-campaign duplicate siblings, producing an incomplete "debate interno" view for admins trying to resolve a dispute.
**Why it happens:** Every other widget in the codebase scopes strictly to the active campaign, so it's the path of least resistance to copy that pattern here too.
**How to avoid:** Follow `VoterDuplicateAssignmentService`'s explicit `withoutGlobalScopes()` precedent; if the report shows one row per document_number group, make sure the underlying siblings query is not silently scoped away.
**Warning signs:** A duplicate group that a user knows exists (from the reassignment UI) doesn't show all its siblings in the report.

### Pitfall 3: Missing `department_id` on `Voter`
**What goes wrong:** Writing the jurisdiction comparison query assuming `Voter` has a `department_id` column (it doesn't — only `municipality_id`).
**Why it happens:** `Campaign` has both `municipality_id` and `department_id`, so it's easy to assume `Voter` mirrors that shape.
**How to avoid:** For departmental-scope campaigns, join through `Municipality::department_id` (see Pattern 7 above) rather than a direct column comparison.
**Warning signs:** A "column not found: department_id" SQL error on `voters` table, or (worse) a silently wrong query if an alias masks the error.

### Pitfall 4: `polling_place_id` being null for many voters
**What goes wrong:** An inner join to `polling_places` in the ranking query silently drops all voters without a resolved polling place, which — depending on how much of the historical data has gone through the Registraduría lookup flow — could be a large fraction of records, making the ranking look artificially small/incomplete without any visible error.
**Why it happens:** `polling_place_id` is populated by an interactive, per-record Registraduría lookup (cache → DB reconstruction → 2captcha), not by a batch backfill; older data may never have gone through it.
**How to avoid:** Surface a visible count of "apoyos sin puesto asignado" alongside the ranking (as a KPI or footnote), so operators understand the ranking isn't the full universe.
**Warning signs:** Ranking totals that don't reconcile with `CampaignStatsOverview`'s total apoyos count (violates REPT-01's "counts reconcile to source records").

## Code Examples

### Rejections consolidation query (verified enum values)
```php
// Source: app/Enums/VoterStatus.php + app/Enums/CallResult.php (read directly)
use App\Enums\CallResult;
use App\Enums\VoterStatus;

$activeCampaign = CampaignContext::currentCampaign();

Voter::query()
    ->when($activeCampaign, fn ($q) => $q->where('campaign_id', $activeCampaign->id))
    ->where(function ($q) {
        $q->whereIn('status', [
                VoterStatus::REJECTED_CENSUS->value,
                VoterStatus::CORRECTION_REQUIRED->value,
            ])
            ->orWhereHas('verificationCalls', fn ($q2) => $q2->whereIn('call_result', [
                CallResult::REJECTED->value,
                CallResult::INVALID_NUMBER->value,
                CallResult::NOT_INTERESTED->value,
            ]));
    })
    ->with(['registeredBy', 'verificationCalls' => fn ($q) => $q->whereIn('call_result', [
        CallResult::REJECTED->value, CallResult::INVALID_NUMBER->value, CallResult::NOT_INTERESTED->value,
    ])]);
```
Note: `VerificationCall` belongs to `Voter` (not the other way), and a voter can have multiple calls with different results across attempts — `->with('verificationCalls')` (filtered) is needed to show *which* rejection reason applied, since the top-level `Voter.status` alone doesn't capture a `CallResult::REJECTED` outcome (call results live only on `VerificationCall`, they don't get rolled up into `Voter.status` automatically per current code — confirmed no such rollup exists in `Voter::booted()` or any observer found).

### Combined flat CSV export skeleton (D-03)
```php
// New file: app/Exports/ApoyosLideresCoordinadoresExport.php
// Pattern verified against app/Exports/VotersExport.php (FromQuery + WithMapping + WithHeadings)
class ApoyosLideresCoordinadoresExport implements FromQuery, ShouldAutoSize, WithHeadings, WithMapping, WithStyles
{
    use Exportable;

    public function query(): Builder
    {
        return Voter::query()
            ->with(['registeredBy.coordinator', 'municipality', 'neighborhood', 'gremio', 'subcategoria']);
        // registeredBy = líder (or coordinator, if they registered it directly)
        // registeredBy.coordinator = the líder's coordinator (User::coordinator() belongsTo)
    }

    public function map($voter): array
    {
        $lider = $voter->registeredBy;
        $coordinador = $lider?->coordinator;

        return [
            $voter->id, $voter->document_number, $voter->duplicate_sequence, $voter->full_name,
            $voter->phone, $voter->status->getLabel(),
            $lider?->name, $lider?->phone, $lider?->email,
            $coordinador?->name, $coordinador?->phone, $coordinador?->email,
        ];
    }
}
```
Caveat: if `registeredBy` IS a coordinator (a coordinator registered the Apoyo directly, no líder in between), `$lider->coordinator` will be null — the export must handle this (show the registering coordinator in the "coordinador" columns directly, líder columns blank), matching how `PD-004`/`docs/DECISIONES.md` structure Líderes/Coordinadores as plain `users` with roles rather than distinct hierarchical tables.

## Open Questions

1. **Coordinator ranking: direct registrations vs. team rollup (their leaders' apoyos)?**
   - What we know: `coordinator_user_id` links `User`→`User` (leader→coordinator); a coordinator ranking could mean apoyos the coordinator personally registered, OR the sum of apoyos registered by all leaders under them.
   - What's unclear: CONTEXT.md's item 2 ("Rankings: ... coordinadores (nuevo)") and item 1 ("informe de líderes+apoyos por coordinador ... meta vs. real") strongly suggest item 1 is a team rollup, but doesn't explicitly say whether the "ranking" in item 2 is the same team-rollup number used for sorting coordinators, or a separate "how many did the coordinator register with their own hands" metric.
   - Recommendation: Plan should default to team-rollup (sum of the coordinator's leaders' valid apoyos) for both item 1 and the coordinator ranking in item 2, since that's the operationally meaningful number for a coordinator's job (managing leaders) — and flag this assumption explicitly in the plan for user confirmation during implementation review.

2. **Should the duplicates report intentionally cross campaign boundaries?**
   - What we know: `VoterDuplicateAssignmentService` explicitly bypasses campaign scopes because duplicate siblings can span campaigns (confirmed bugfix in STATE.md's 02.1-10 entry).
   - What's unclear: CONTEXT.md's "Established Patterns" section says campaign isolation applies to all new widgets "except where the report itself explicitly crosses campaigns, which does not apply here" — but this may have been written without considering that duplicates specifically DO cross campaigns per the 02.1-10 precedent.
   - Recommendation: Plan should default to campaign-scoped (matching every other widget and the explicit CONTEXT.md guidance) for the *report's row set* — i.e., only show duplicate groups where at least one sibling belongs to the active campaign — but when displaying a group, show ALL its siblings regardless of campaign (with a campaign column/badge per sibling) so cross-campaign disputes remain visible without violating the "don't leak other campaigns' unrelated data" spirit. This should be called out explicitly to the user/planner as a judgment call, not silently decided.

3. **"Índice de calidad de dato" KPI — include or defer?**
   - What we know: Explicitly marked as Claude's Discretion in CONTEXT.md; client requested it as "valor agregado."
   - What's unclear: No design was discussed (formula, which of the 6 reports it lives on, whether it's a `StatsOverviewWidget` or a column within one of the ranking tables).
   - Recommendation: If included, implement as a 7th lightweight `StatsOverviewWidget` (`DataQualityIndexWidget`) with 3 `Stat::make()` cards (% válidos, % duplicados, % fuera de jurisdicción), computed from the same queries as reports 2/4/6 — cheap to add given the underlying queries already exist, but should be explicitly scoped in/out during planning rather than assumed.

4. **Drill-through (REPT-04) — any of these reports link to underlying record lists?**
   - What we know: None of the 3 existing widgets implement drill-through today (no precedent in this codebase).
   - What's unclear: Whether this phase should introduce the first drill-through pattern (e.g., clicking a coordinator's row in the ranking navigates to a filtered `VoterResource` list), or whether that's out of scope for this ad-hoc phase.
   - Recommendation: Treat as out of scope unless the planner decides otherwise — CONTEXT.md doesn't mention it, and introducing a new interaction pattern (row click → filtered navigation) is a bigger lift than the rest of this phase's mechanical reporting work.
